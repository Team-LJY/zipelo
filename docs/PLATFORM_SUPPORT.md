# 플랫폼 지원 계획

## 지원 목표와 미검증 상태

2026-11-09 기준 계획 문서다. Windows 우선 구현을 유지하면서 Ubuntu 24.04 LTS와 Ubuntu 26.04 LTS를 개발 및 정식 지원 목표로 관리한다. Ubuntu를 Windows 전체 완료 뒤의 후보로 두지 않는다. 현재 개발 기준은 x64이며 ARM64, x86, macOS와 다른 배포판은 검증된 대상으로 안내하지 않는다.

**현재는 개발 검증 단계이며 일반 사용자용 설치 파일과 출시 준비는 완료되지 않았다.** Windows round5의 기존 C# 62개 및 일부 생성 UI 흐름은 통과 보고가 있다. 새 해제를 포함한 round6는 Core 41개 통과, Runtime 검사 프로젝트 컴파일 실패로 56개 미실행이다. 97개 전체 검증과 Ubuntu 실제 검증은 미완료이며 일반 배포용 생성과 해제는 계속 비활성이다.

"지원 목표"는 요구사항, "구현"은 소스 존재, "검증"은 식별된 산출물을 해당 환경에서 실행한 근거를 뜻한다. 각 Ubuntu LTS에서 직접 검증하기 전에는 지원 완료로 표시하지 않는다. 문서 작성 환경이 Linux라는 사실도 Ubuntu 두 버전의 실행 증거가 아니다. 플랫폼별 지원 완료와 전체 기능 요구 충족은 따로 판단한다.

- Windows: Windows 11 x64가 현재 개발 기준이며 최소 지원 빌드는 미확정이다. WPF UI와 Core/Runtime/Worker, 개발용 작업자 배치가 작성됐다. 최종 설치 패키지, 기본 연결, 안전 출력과 전체 기능 검증은 남아 있다.
- Ubuntu 24.04 LTS x64: 정식 지원 목표다. 별도 UI, linux-x64 배포, .deb 설치와 연결 및 안전 출력 경로를 준비한다. 이 LTS에서의 빌드, GUI, 실제 ZIP과 설치 실행 근거는 아직 없다.
- Ubuntu 26.04 LTS x64: 정식 지원 목표다. 24.04와 별개로 의존성, 세션, 설치, 업데이트와 제거를 검증한다. 24.04 성공을 이 버전의 통과로 복사하지 않는다. 이 LTS에서의 실행 근거는 아직 없다.

공통 설계와 역할별 병행 작업은 [기획서](PLANS.md), 작업자 능력과 구현 한도는 ZIP 런타임 (`docs/ZIP_RUNTIME.md`, 별도 구현/검증 브랜치)을 따른다. 이 문서는 계획 및 플랫폼 상태만 소유하며 UI/엔진 후보를 임의로 채택하거나 구현 담당자의 결과를 대신 선언하지 않는다.

## 확인된 구현과 실행 근거

기획 담당자가 읽은 소스 기준 Windows는 `src/Zipelo.Desktop/`의 WPF, Ubuntu는 `src/Zipelo.Ubuntu/`의 별도 UI다. 양쪽 UI에 ZIP 목록과 생성/새 파일 게시 연결 코드가 작성됐다. 생성은 일반 Debug/Release에서 비활성이고 명시적 `ZipeloCreationValidation` 개발 검증 빌드에서만 허용한다. 이 설정은 안전성 검증 완료를 뜻하지 않으며 일반 배포물에는 지정하지 않는다. 해제는 계속 비활성이다. Ubuntu UI의 실제 실행 및 파일 선택 검증은 남아 있다. 상세는 Ubuntu UI 기록 (`docs/UBUNTU_UI.md`, 별도 구현/검증 브랜치)을 따른다.

Runtime/Worker에는 비암호화 ZIP 목록과 메모리 생성, 입력/프레임 한도와 취소/시간 초과 후 종료 확인 코드가 있다. OS별 파일명 정책과 작업자 이름 및 `NewZipPublisher.PublishAsync`도 작성됐으나, 구현 경로가 있다는 능력 표시는 OS별 안전성 통과를 뜻하지 않는다. 메모리 생성과 디스크 저장은 구분한다. 암호, 분할, 복구, 미리보기와 안전 해제의 최종 제품 요구도 미완료다.

### 최신 Windows 실행과 과거 결과

프로젝트 검증 담당자의 결과를 총괄이 전달한 보고에 근거한다. 기획 담당자가 VM에 접속하거나 재실행하지 않았다.

- Windows round5 C# 62개 전부 통과 및 Desktop/Core/Runtime/Worker 빌드 경고 0, 오류 0이 전달됐다. 새 ZIP 파일 저장/내용 일치, 기존 파일과 입력 충돌 보존 및 부모/최종 symlink 거절을 해당 실행에서 확인했다고 보고됐다.
- 이후 공유 생성 스트림 수정이 반영된 개발 검증 UI에서 생성, 충돌 시 기존 파일 보존과 파일 선택 취소 후 재시도 성공이 전달됐다. 이번에 읽은 공유 `ZipCreationWorkflow.cs`의 SHA-256은 전달된 수정값 `1529b854f31bfb321bbdfeff97cdb1e5d69ac00281873ce881ffea3dc013789f`와 일치한다. 실제 UI 실행은 총괄 전달 결과이며 기획 담당자의 실행 결과가 아니다.
- 정확한 round5 스냅샷 시각/전체 해시와 UI 재검증 파일 목록은 이번 전달에 없다. 후속 시작 인수 처리와 메모리 해제 등 현재 공유 소스 전체에 통과를 확장하지 않는다.
- 이전 2026-11-09T13:59:27.796888Z의 57/60과 게시 3개 실패는 과거 기록이다. 후속 62개 실행에서 게시 사례가 통과했으므로 현재 실패 상태로 남기지 않는다. 과거 39개 통과도 해당 시점의 범위에만 해당한다.

### round6의 컴파일 및 실행 한계

2026-11-09T14:44:04.604469Z의 src/tests 102개 독립 스냅샷에서 Desktop/Core/Runtime/Worker 빌드는 경고 0, 오류 0이며 Core 41개는 통과했다고 보고됐다. RuntimeTests는 당시 `tests/runtime/ExtractionPublicationTests.cs(125,22)`의 CS0266으로 컴파일부터 실패해 56개 전부 미실행이다. 타입 오류의 최소 수정은 보고됐지만 수정 후 동일 스냅샷의 재실행 성공 근거는 아직 없다.

round6 고정 소스에서는 `NewFolderPublisher.IsSupportedPlatform=false`였으며 Windows/Linux 모두 게시 진입이 차단돼 있었다. 당시 폴더 게시 수용 검사 8개는 구현 게이트에 걸리는 사례였으나 실제 실행되지 않았다. 이 과거 소스/검사 상태를 후속 원본의 현재 상태로 사용하지 않는다.

### round6 이후의 폴더 게시 구현(미검증)

2026-11-10 KST에 확인한 ZIP 엔진 커밋 `9f36e037bc5f1b2f1e67caa3528a3a344ec1107b`와 대응 원본에는 핸들 기준 생성, 내용 재검증, 덮어쓰기 금지 게시 및 소유 항목 정리가 연결돼 있다. `NewFolderPublisher.IsSupportedPlatform`은 Windows/Linux x64에서 구현 진입 가능성을 나타내며, 파일시스템/권한 조건 충족이나 실제 실행 통과를 뜻하지 않는다.

- Windows는 로컬 NTFS와 제한된 쓰기 ACL/소유자 조건에서만 게시를 시도하는 구현이다. 현재 사용자, SYSTEM, Administrators 외 계정의 쓰기 허용, reparse 및 해석할 수 없는 보안 조건은 거부한다.
- Linux는 XFS와 필요한 openat2/statx/renameat2 기능, 부모가 현재 euid 소유이며 그룹/기타 쓰기가 없는 조건으로 제한한다. ext2/ext3/ext4는 공통 식별값만으로 구분할 수 없어 임시 항목 생성 전에 거부한다. ext4 게시나 Ubuntu 기본 파일시스템에서의 저장 완료를 약속하지 않는다.
- 위 조건이 확인되지 않으면 실패 폐쇄하며 경로 기반 우회나 기존 결과와의 병합/덮어쓰기를 허용하지 않는다. 같은 사용자 권한의 악성 프로그램이나 관리자에 의한 임시 트리 변조까지 방어한다고 주장하지 않는다.

이 후속 구현의 C# 컴파일과 실제 Windows NTFS 및 Linux XFS 게시/취소/경합/정리는 미검증이다. 일반 해제 능력 `SupportsSafeExtraction=false`와 일반 UI 비활성은 유지한다. 소스의 구현 진입점, OS별 제한 조건, 실행 통과 및 사용자 기능 활성화를 각각 구분한다.

### 새 해제와 Ubuntu 및 일반 배포 상태

작업자 메모리 ZIP 해제와 후속 폴더 게시 코드는 소스 작성 및 검토 단계이며 실제 새 C# 실행은 미완료다. round6 당시 검사 기록 (`tests/extraction/coverage.json`, 별도 구현/검증 브랜치)의 97개 등록 및 Python 33개 통과를 현재 후속 코드의 실행 결과로 사용하지 않는다. 폴더 게시의 새 플랫폼 계약과 수용 검사는 검증 담당자가 조정 중이므로 현재 사례 수와 skip/pass 상태는 실제 최신 검사 및 OS 실행 결과로 확인해야 한다. 해제 계약 (`docs/ZIP_EXTRACTION.md`, 별도 구현/검증 브랜치)의 원본/기존 대상 보존과 임시 트리 안전 조건도 별도 OS 검증이 필요하다.

Ubuntu UI 및 OS 정책이 작성돼도 두 LTS의 빌드/GUI/기능/안전 게시/설치 검증은 미완료다. 현재 호스트 Ubuntu 26.04.1 LTS와 GNOME Wayland/XWayland 전달 정보는 앱 실행 근거가 아니며 24.04 검증 환경도 미확인이다. Windows round5나 개발 검증 UI 성공을 Ubuntu 통과로 계산하지 않는다.

README는 설치 파일 부재와 다운로드 준비를 명시한다. `packaging/`의 Windows 설치 및 Ubuntu .deb/desktop/MIME 초안은 검증된 배포물, 고지와 manifest를 요구하며 실제 패키지 생성이나 설치를 완료한 결과가 아니다. 시작 인수 처리는 소스 작성 후 실제 OS 검증 전이므로 파일 연결 등록 차단을 유지한다. 개발용 build/publish 및 명시적 생성 검증 빌드는 일반 사용자용 설치/다운로드 경로가 아니다.

Windows의 단일 새 ZIP 게시와 일부 생성 UI 흐름이 통과했어도 SDK 없는 깨끗한 설치, 업데이트/제거, 기본 연결, 전체 형식/암호/복구 요구와 일반 배포용 활성화는 미완료다. 해제 저장의 안전 조건과 OS 실행 검증 전에는 해제를 켜지 않는다. 릴리스 공개와 업로드도 별도 승인 범위로 유지한다.

## 공통 기반과 OS별 경계

- 공통: Core 작업 계약, 상태와 오류, 원본 보존, 누적 예산, 취소 의미, IPC 프로토콜과 기능별 능력 정보를 유지한다. UI 프로세스가 신뢰할 수 없는 압축을 직접 파싱하지 않는다.
- UI: Windows WPF를 보존하고 Ubuntu용 UI 진입점을 별도로 둔다. WPF는 Windows 전용이므로 Ubuntu에서 같은 화면을 그대로 실행한다고 설명하지 않는다. [Microsoft WPF 설명](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)
- Ubuntu UI 후보: 프론트엔드 담당자가 공식 지원 OS와 버전, 라이선스, X11/Wayland 경로 및 의존성을 비교해 근거를 기록한다. 기본 오픈소스 도구와 유료 또는 제한적 WPF 호환 제품을 혼동하지 않는다. 도구 선정과 프로젝트 뼈대는 실제 LTS 지원 검증을 대신하지 않는다.
- 파일 정책: 대상 OS와 실제 파일시스템에 맞게 구분자, 유효 이름, 대소문자와 충돌 판단을 분리한다. Linux의 합법적 이름을 Windows 예약 이름/문자 규칙으로 일괄 거부하지 않는다. `A.txt`와 `a.txt`를 조용히 합치거나 이름 정규화로 덮어쓰지 않는다. 서로 다른 정책으로 이동 시 충돌을 명시한다.
- 작업자 경로: 앱 설치 위치 기준의 신뢰할 수 있는 절대 경로로 고정한다. Windows apphost의 `.exe` 이름을 Linux에 강요하지 않는다. 현재 작업 디렉터리, 압축파일 위치나 사용자 데이터에서 실행 파일을 찾지 않는다. OS별 실행 권한과 필수 의존 파일 누락, 시작 및 프로토콜 실패를 검사한다.

## 설치와 실행 경험

일반 사용자는 SDK나 컴파일러 설치, 소스 빌드 없이 설치하고 실행할 수 있어야 한다. 자체 포함 런타임을 우선 검토하고 필수 시스템 라이브러리는 패키지 의존성으로 명시한다. 자체 포함 배포가 모든 OS 라이브러리까지 포함하거나 오프라인 실행을 자동 보장한다고 설명하지 않는다. 설치 과정에 추가 다운로드가 있으면 대상과 필요성을 안내한다.

### Windows

- 쉬운 GUI 설치와 설치 완료 후 실행을 제공하는 최종 패키지를 준비한다. 현재 Windows 폴더 게시 프로필과 별개로 검증한다.
- 가능한 설치 범위를 명확히 안내하고 앱 실행에 관리자 권한을 상시 요구하지 않는다. 설치 권한과 작업자 권한은 구분한다.
- UI와 작업자 런타임 중복을 포함한 실제 설치 크기를 측정한다. 아직 30MB 목표 달성을 약속하지 않는다.
- 지원 형식 처리 앱 등록과 실제 기본 앱 선택은 구분한다. 기본 앱 변경은 사용자가 Windows의 지원되는 설정 흐름에서 선택하며 강제 변경하지 않는다. [Windows 기본 앱 플랫폼](https://learn.microsoft.com/en-us/windows/apps/develop/windows-integration/default-apps-platform)

### Ubuntu 24.04 및 26.04 LTS

- x64용 .deb를 계획 산출물로 두고 패키지 아키텍처 `amd64`와 배포 RID `linux-x64`의 대응을 확인한다. 양쪽 LTS에서 의존성을 충족하는 경우에만 같은 패키지를 공용으로 제공한다.
- 내려받은 패키지의 GUI 설치, 명확한 인증 요청, 메뉴/런처 실행과 파일 열기를 검증한다. GUI 설치 도구의 실제 제공 여부와 제한은 각 이미지에서 확인한다. 일반 사용자의 수동 SDK 설치나 터미널 빌드를 기본 경로로 삼지 않는다.
- .deb의 파일 목록, 의존성, 데스크톱 항목, 아이콘과 필요한 MIME 메타데이터를 검토한다. 패키지 소유 파일과 사용자 설정/데이터를 분리하고 시스템 패키지 관리와 충돌하지 않게 한다. [Debian 패키지와 데스크톱 통합 지침](https://www.debian.org/doc/debian-policy/ch-opersys.html)
- 앱 메뉴와 파일 관리자에서 실행되며 한글, 공백과 특수문자 경로가 하나의 올바른 인자로 전달돼야 한다. 셸 문자열 조합으로 파일명을 실행하지 않는다. 데스크톱 항목의 `Exec`는 검증된 파일 인자 전달 방식을 사용한다. [Desktop Entry Exec 규격](https://specifications.freedesktop.org/desktop-entry/latest/exec-variables.html)

## 기본 앱과 제외 형식

처리 가능한 형식, 설치 시 처리 앱 등록, 사용자의 기본 앱 선택과 실제 적용 결과를 따로 관리한다. 등록은 현재 제품에서 검증돼 공개한 형식의 허용 목록으로 제한한다. 엔진이 읽을 수 있다는 이유만으로 모든 컨테이너를 등록하지 않는다.

- JAR는 Windows 확장자/처리 앱 등록, Ubuntu .deb 설치 스크립트, `.desktop`의 `MimeType`, MIME XML과 기본 앱 변경 대상에서 모두 제외한다. `.jar`와 대소문자 변형, Java archive MIME 변형을 검사한다.
- APK, WAR, DOCX, XLSX, PPTX 등 추가 컨테이너의 제품 제외 범위는 미확정이다. 별도 승인과 기능 검증 없이 연결 허용 목록에 넣지 않는다. JAR 제외를 이들 형식의 최종 제품 제외 확정으로 확대하지 않는다.
- Ubuntu는 알려진 압축 MIME의 처리 앱 등록과 기본 앱 선택을 분리한다. 범용 바이너리 MIME이나 광범위한 glob, 기존 MIME 재정의로 JAR나 문서 형식을 ZIP에 흡수하지 않는다. 새 MIME 정의가 필요한지 먼저 확인한다. [Desktop Entry 등록 키](https://specifications.freedesktop.org/desktop-entry/latest/recognized-keys.html)
- 설치와 업데이트의 유지관리 스크립트가 사용자 `mimeapps.list`를 임의로 바꾸거나 `xdg-mime default`로 무조건 기본 앱을 바꾸지 않는다. 명시적 선택 UI에서 대상 목록과 [적용]/[나중에]를 제공한다. 동의 후에도 허용 목록 안의 사용자 선택만 적용한다.
- 앱 등록으로 파일 관리자의 선택 후보가 되거나 기존 기본 앱이 없는 환경에서 선택될 가능성과, 사용자의 기존 기본 앱을 명시적으로 변경하는 동작을 구분한다. 기본 앱 결과는 환경에서 읽어 확인하고 미적용/일부 적용을 성공으로 표시하지 않는다. [MIME 기본 앱 규격](https://specifications.freedesktop.org/mime-apps/latest/default.html)
- 앱 내부 파일 선택, 끌어놓기와 실행 인자에도 같은 제외 정책을 적용한다. 확장자를 바꿨다고 원래 형식을 자동 신뢰하지 않는다. 지원 판단과 구조 확인은 엔진 경계를 따르며 제외 정책을 우회하지 않는다.
- 업데이트는 기존 선택을 보존한다. 제거 시 앱 소유 등록만 정리하고 사용자가 이후 선택한 다른 앱을 덮어쓰지 않는다. 과거 연결을 일괄 복원한다고 약속하지 않는다.

이 문서 작성 중 실제 기본 앱이나 MIME 데이터베이스를 변경하지 않았다. 관련 실기 검증은 별도로 승인된 폐기 가능한 환경에서 수행한다.

## 안전한 출력과 작업자 제한

### 새 ZIP 파일 게시와 해제 구분

사용자가 명시적으로 고른 새 목적지에 완성된 메모리 ZIP을 게시하는 API는 기존 파일 무덮어쓰기와 원본 보존을 검증한다. 임시 파일의 생성 소유권, 실패/취소 후 정리, 게시 직전 목적지 충돌과 게시 후 늦은 취소의 결과를 정의한다. 디스크 부족, 권한 오류와 대상 경로 교체에서도 기존 파일 및 목적지 밖 파일을 바꾸지 않아야 한다. 정리에 실패하면 이를 숨겨 성공으로 표시하지 않는다.

단일 ZIP 게시 API 통과가 여러 항목을 새 폴더에 게시하는 해제 저장 계층의 완료를 뜻하지 않는다. 후속 폴더 게시 내부 API는 제한된 OS 조건에서만 진입하며 조건 미충족 시 실패 폐쇄한다. 일반 해제 capability/UI는 문자열 검사나 구현 진입 가능 값만으로 활성화하지 않고 실제 OS 검증 전까지 비활성으로 유지한다.

- Windows: 링크, reparse point/junction, 대상 핸들 및 파일 정체성 확인, 경로 교체, 드라이브/장치/UNC/ADS, 대소문자와 이름 정규화 충돌을 구분해 검증한다.
- Ubuntu: 기존 및 끊어진 symlink, 상위 디렉터리 symlink, 경로 교체, 원본과 같은 파일을 가리키는 경로/하드 링크, 권한 및 대소문자 충돌을 검증한다. 문자열 검사로 symlink 경쟁 방어가 완료됐다고 안내하지 않는다.
- 공통: 입력 파일을 수정하지 않고 덮어쓰기 충돌 시 기존 바이트를 보존한다. 최종 게시 전후 취소를 구분하며 본 작업이 소유하지 않은 임시/대상 파일을 삭제하지 않는다. 실제 파일시스템의 링크 및 이름 비교 특성을 시험 기록에 남긴다.

### 프로세스와 자원

현재 구현 한도는 입력 합계와 생성물 각각 16 MiB, IPC 프레임 32 MiB, 항목 수 1024, 항목 이름 1024자, 요청 시간 최대 5분이며 호출자의 더 작은 `JobLimits`도 적용한다. Desktop 목록 경로는 2분 제한을 사용한다. 정확한 예산 계산과 변경 시점은 런타임 문서 (`docs/ZIP_RUNTIME.md`, 별도 구현/검증 브랜치)와 실제 코드를 따른다.

프레임 제한은 JSON/메모리 복사와 압축 메타데이터를 포함한 전체 프로세스 메모리 상한이 아니다. 별도 작업자는 현재 사용자 권한으로 실행하며 보안 샌드박스, CPU/메모리 강제 제한과 네트워크 차단이 완성된 것은 아니다.

- Windows Job Object 등과 Linux 자원/권한 제한의 구현 및 실제 효과를 각각 기록한다. 도구 이름이나 설계 제안만으로 적용 완료라고 쓰지 않는다.
- 입력/출력/프레임 한도 직전과 초과, 실제 최대 메모리, 시간 초과, 취소, 종료 대기 실패와 자식 프로세스 잔존을 OS별로 검사한다.
- 필수 파일 누락, 실행 권한 없음, 시작 실패, 잘못된/끊긴 프레임, 비정상 종료에서 성공 결과를 반환하지 않고 화면이 다음 작업을 받을 수 있어야 한다.

## 환경별 수용 기준과 증거

모든 테스트 코드, 샘플, 회귀 스크립트와 테스트 전용 임시 데이터는 프로젝트 루트 `tests/` 아래에만 둔다. 기획 문서는 검증 기준만 정의하며 다른 담당자의 테스트를 중복 구현하지 않는다.

### 공통 설치 생명주기

1. 개발 도구 없는 깨끗한 Windows x64, Ubuntu 24.04 LTS x64, Ubuntu 26.04 LTS x64를 각각 식별한다. 배포물 해시, 앱/런타임 버전, OS 빌드, 아키텍처, 파일시스템, 시스템 의존성과 네트워크 조건을 기록한다.
2. 설치 취소, 의존성 부족, 권한 거절, 공간 부족과 재시도를 검사한다. 설치 완료 뒤 SDK 없이 메뉴/바로가기 실행과 ZIP 목록 열람을 확인하고, 안전 게시가 연결되면 새 ZIP 생성 및 재열람과 바이트 비교를 검사한다. 미구현 해제를 성공 시나리오로 대체하지 않는다.
3. 기존 버전에서 업데이트할 때 사용자 설정, 입력/결과 파일과 기존 기본 앱 선택이 보존되는지 확인한다. 실행 중 작업자의 처리와 실패/중단 후 일관된 앱 상태 및 복구 방법을 기록한다. 새 버전 UI와 이전 작업자가 섞이면 명확히 실패해야 한다.
4. 일반 제거와 재설치에서 앱 소유 실행 파일/작업자/등록을 정리하고 원본, 결과 파일과 타 앱 연결은 보존한다. 남기는 사용자 설정과 정리 실패를 안내한다. 제거 후 깨진 런처나 앱 소유 연결이 남는지도 확인한다.
5. 연결 변경에 동의하지 않은 설치/업데이트에서 기존 기본 앱이 유지되고 JAR 및 제외 확정 형식이 앱 등록 목록에 추가되지 않는지 확인한다. 동의한 경우도 선택한 허용 형식만 적용되며 실제 열기 결과와 표시 상태가 일치해야 한다.

### Ubuntu 각 LTS의 UI와 세션

- 24.04와 26.04 각각에서 X11 및 Wayland 경로의 제공 여부와 선택한 UI 도구의 지원 수준을 기록한다. 실제 X11 세션, Wayland 네이티브와 Wayland 위 XWayland 실행을 구분한다. OS/도구가 제공하지 않는 조합은 사유와 남은 결정을 기록하고 통과로 계산하지 않는다.
- 제공되는 각 검증 경로에서 창 표시와 재실행, 파일 선택/취소, 끌어놓기, 키보드 이동/단축키, 암호창 포커스/취소, 오류/작업 취소 후 복귀를 검사한다. 암호 기능이 미구현이면 그 제한을 표시하고 암호 처리 통과로 기록하지 않는다.
- 100%, 125%, 150%, 200% 배율과 가능한 혼합 배율에서 텍스트/필수 버튼/파일 선택 창을 확인한다. 해당 세션에서 지원하지 않는 배율 조건도 별도 기록한다. 한글 입력과 화면 읽기 접근성도 검증한다.
- 일반 사용자 권한과 실제 패키지 설치 경로에서 작업자 실행, 안전 출력, 파일명 및 대소문자 보존을 확인한다. 개발 소스 경로나 시스템 `dotnet`이 우연히 발견돼 성공한 결과를 사용자 배포 통과로 계산하지 않는다.

### 완료 표시 규칙과 남은 환경

기존 Windows round5 62개 통과와 생성 스트림 수정 후 개발 검증 UI 성공은 해당 검증 범위의 근거로 남긴다. 이전 57/60의 게시 실패는 후속 통과로 갱신됐으나 새 해제 검사까지 합친 97개 전체 통과로 표시하지 않는다. Ubuntu 각 LTS는 독립적인 설치 생명주기, UI/세션, 실제 작업자와 공개 기능, 제외/기본 연결 및 안전 출력 결과가 있어야 플랫폼 지원 완료를 판단한다. 실행하지 않은 항목은 미실행, 구현 없는 항목은 미구현, 제한으로 불가능한 항목은 근거와 결정 필요로 기록한다. 완료된 일부 기능으로 전체 제품 요구를 완료 처리하지 않는다.

추가로 필요한 환경은 Windows x64 검증 환경, Ubuntu 24.04 LTS x64 및 26.04 LTS x64의 깨끗한 데스크톱 이미지와 제공되는 세션, 선택한 UI 도구의 빌드 의존성과 패키지 검사 도구다. 구체적인 도구/패키지 목록은 UI 및 검증 담당자의 선정 결과로 확정한다. 이번 기획 검토에서는 OS, SDK, 패키지와 권한을 설치/변경하거나 VM을 실행하지 않는다. 문서와 자체 코드의 MIT LICENSE만 담당 브랜치로 분리하며 실제 설치와 바이너리 배포를 수행하지 않는다.
