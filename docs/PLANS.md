# Zipelo 기획서

쉽게 설치하고 빠르게 압축하고 풀 수 있는 가벼운 오픈소스 압축 프로그램을 목표로 한다.

이 문서는 제품 요구사항과 설계, 구현 및 검증 상태를 구분해 정리한다. 요구사항이나 소스 파일의 존재가 기능 완료나 성능 검증을 의미하지 않는다. 검토안은 기술 검증과 사용자 결정에 따라 확정한다. 현재 상태는 2026-11-09 로컬 파일과 담당자 검증 기록을 기준으로 한다.

현재는 개발 검증 단계이며 일반 사용자용 출시와 설치 패키지는 준비되지 않았다. 기존 Windows round5의 C# 62개 통과와 생성 UI 성공 보고는 그 범위의 결과다. 신규 해제를 포함한 round6에서는 Core 41개가 통과했지만 Runtime 검사 프로젝트가 컴파일에 실패해 56개 모두 미실행이다. 총 97개 전체 통과가 아니다. 일반 배포용 생성과 해제, Ubuntu 두 LTS의 실제 검증은 미완료다.

## 1. 제품 방향과 결정 상태

### 확정 사항

- 제품명은 Zipelo로 한다.
- 경량성과 빠른 처리, 쉬운 설치를 우선한다.
- 압축과 압축 해제를 핵심 기능으로 삼는다.
- ZIP, 7Z, RAR, TAR.GZ 등 일반 압축파일을 최대한 폭넓게 해제한다.
- JAR처럼 다른 용도로 사용되는 컨테이너는 지원 대상에서 제외한다.
- 암호 설정과 암호 입력, 접근 가능한 항목의 미리보기를 제공한다.
- 손상 파일은 복구 가능한 범위에서 자동 복구를 시도한다.
- README 상단에 제품명, 간단한 소개, 눈에 띄는 다운로드 버튼을 배치한다.
- GitHub Releases를 배포 경로로 사용한다.
- Windows 우선 구현을 유지하면서 Ubuntu 24.04 LTS와 Ubuntu 26.04 LTS를 개발 및 정식 지원 목표로 관리한다. Ubuntu 준비는 Windows 전체 완료 후로 미루지 않는다.
- 현재 개발 기준은 x64다. 각 OS의 실제 검증 전에는 지원 완료로 표시하지 않으며 다른 아키텍처를 검증했다고 안내하지 않는다.
- Zipelo 자체 작성 코드에는 MIT 라이선스를 적용한다. 비상업적 이용 제한은 두지 않는다.

### 개발 가정과 검토안

| 항목 | 초기 제안 | 확정에 필요한 조건 |
| --- | --- | --- |
| 플랫폼 개발 기준 | Windows 11 x64 우선 구현, Ubuntu 24.04 LTS 및 26.04 LTS x64 병행 준비 | Windows 최소 빌드 확정과 각 Ubuntu LTS의 독립 실행 및 설치 검증 |
| UI 구성 | Windows는 .NET 10 WPF 유지, Ubuntu는 공통 Core/Runtime을 사용하는 별도 UI 경로 | Ubuntu 도구의 공식 OS 지원과 자유 라이선스 확인, 각 OS의 접근성 및 배포 검증 |
| 압축 엔진 | SharpCompress, RAR 제외 7-Zip과 libarchive 등의 후보 검토 | 버전별 기능, 출처, 포함 코드와 배포 조건 검증. 채택 미확정 |
| 복구 우선순위 | ZIP 복구부터 제공 | 손상 유형별 성공 여부와 오탐 검증 |
| 미리보기 | 이미지와 일반 텍스트 우선 | 처리 비용과 안전한 렌더링 검증 |
| 추가 환경 | ARM64, macOS와 지정 Ubuntu 외 배포판 | 별도 요구와 우선순위 결정. 현재 검증 범위 아님 |

Windows WPF 화면을 Ubuntu에서 그대로 실행하는 계획은 두지 않는다. 공통 계약과 OS별 UI, 설치, 파일 연결, 저장 및 작업자 제한을 지금부터 분리한다. 플랫폼별 목표, 현재 구현과 미검증 기준은 [플랫폼 지원 계획](PLATFORM_SUPPORT.md)에서 관리한다.

## 2. 대상 사용자와 제품 범위

주요 사용자는 GitHub나 압축 형식에 익숙하지 않아도 파일을 다운로드하고 설치한 뒤 바로 압축을 풀고 싶은 일반 사용자다.

주요 사용 시나리오는 다음과 같다.

1. 압축파일을 더블클릭해 목록을 보고 원하는 위치에 압축을 푼다.
2. 파일이나 폴더를 선택해 ZIP 또는 7Z 파일을 만든다.
3. 암호가 필요한 항목에 접근할 때 암호를 입력한다.
4. 압축을 전부 풀기 전에 접근 가능한 이미지나 텍스트를 확인한다.
5. 손상된 압축파일에서 읽을 수 있는 항목을 확인하고 별도로 저장한다.

초기 범위는 압축, 압축 해제, 목록 열람, 암호, 미리보기, 제한된 복구, 설치와 기본 앱 설정 안내다. 클라우드 저장소, 계정, 광고, 범용 문서 편집 기능은 초기 범위에서 제외하는 안을 제안한다.

## 3. 압축 형식 지원 계획

| 구분 | 대상 형식 | 초기 계획 |
| --- | --- | --- |
| 생성 및 해제 우선 | ZIP, 7Z | 일반 생성과 해제, 암호 기능을 우선 검증 |
| 생성 및 해제 확장 | TAR, TAR.GZ, TAR.BZ2, TAR.XZ | 중첩된 TAR를 한 번의 사용자 작업으로 해제 |
| 해제 전용 | RAR, RAR5, CAB, LZH, LZMA, Z 등 | 엔진과 샘플 검증 후 지원 범위 확정 |
| 분할 압축 | 분할 7Z, 분할 RAR | 조각 자동 탐색과 누락 안내 우선 |
| 추가 검토 | Zstandard 계열, ALZ, EGG | 라이선스, 구현 비용, 사용 수요 검토 |
| 제외 | JAR | 지원 목록과 기본 앱 연결 대상에서 제외 |
| 제외 후보 | APK, WAR, DOCX, XLSX, PPTX 등 | 앱이나 문서용 컨테이너의 제외 범위 확인 |

이 표는 제품의 지원 완료표가 아니다. .NET 기본 기능의 비암호화 ZIP 목록과 메모리 생성 작업자가 작성됐으나 전체 형식 엔진, 안전한 파일 게시와 해제의 완료를 의미하지 않는다. 암호화 RAR와 구형 솔리드 RAR는 검증 중으로 유지하며, 특정 후보의 한계를 이유로 제품 미지원이나 출시 제외를 확정하지 않는다. 기능 범위를 줄여야 한다면 근거와 대안을 제시해 사용자의 결정을 받는다.

압축 생성과 해제의 지원 범위는 구분한다. 7-Zip 계열 엔진을 채택할 경우 RAR 생성은 제공하지 않는다. 엔진이 읽을 수 있는 모든 형식을 Zipelo의 기본 앱 연결 대상으로 등록하지 않는다.

확장자만으로 정상 파일 여부나 지원 여부를 판단하지 않는다. 실제 서명과 구조를 확인하고, 제외 정책을 적용한 뒤 지원 엔진으로 연다. 같은 확장자에서도 압축 방법, 암호화 방식, 분할 방식에 따라 지원이 달라질 수 있다.

출시 시에는 형식별 목록 열람, 해제, 생성, 암호화, 분할 지원 여부를 공개한다. 지원이 검증되지 않은 형식을 포함해 "모든 압축파일 지원"으로 안내하지 않는다.

## 4. 핵심 화면과 사용 흐름

### 첫 화면

- [압축파일 열기]와 [새로 압축하기]를 주요 행동으로 배치한다.
- 파일을 끌어다 놓아 열거나 압축할 수 있게 한다.
- 고급 옵션은 기본 흐름을 방해하지 않는 위치에 둔다.
- 키보드 조작, 포커스 표시, 화면 배율과 스크린 리더 접근성을 고려한다.

### 압축 해제

압축파일 열기 → 목록 표시 → [압축 풀기] → 저장 위치 확인 → 진행 상태 → 완료 후 [폴더 열기]

- 기본 목적지는 압축파일 이름과 같은 새 폴더로 제안한다.
- 전체 해제와 선택 항목 해제를 제공한다.
- 같은 이름의 파일이 있으면 덮어쓰기, 건너뛰기, 이름 변경을 선택하게 한다.
- 부족한 공간이나 쓰기 권한 문제는 사용자가 해결할 수 있는 행동과 함께 안내한다.
- TAR.GZ 같은 복합 형식은 사용자가 중간 TAR 파일을 다시 열지 않아도 최종 파일을 얻도록 한다.

### 압축 생성

파일 선택 → 이름과 저장 위치 확인 → 필요하면 형식과 암호 설정 → [압축하기] → 완료

- 기본 형식은 ZIP, 기본 압축 수준은 "균형"으로 제안한다.
- "빠르게", "균형", "작게"를 제공하고 세부 설정은 고급 옵션에 둔다.
- 암호화 옵션을 지원하지 않는 형식에서는 해당 기능을 사용할 수 없는 이유를 표시한다.
- 생성 실패나 취소 시 원본 파일은 보존하고 미완성 결과를 완성된 파일처럼 표시하지 않는다.

### 공통 진행 상태

진행률, 처리 용량, 현재 작업, 취소 버튼을 제공한다. 전체 용량을 알 수 없는 작업에는 부정확한 백분율 대신 처리한 용량을 표시한다. 암호 입력 대기와 오류 대기는 실제 처리 중인 상태와 구분한다.

## 5. 암호 설정과 입력

- ZIP과 7Z 생성 시 AES-256을 우선 지원하는 안으로 검증한다.
- 7Z 생성에는 파일명 숨기기 옵션을 제공한다.
- 암호 설정에는 재입력과 표시 전환을 제공한다.
- 기존 암호화 파일은 엔진이 지원하는 암호화 방식에 따라 해제한다.
- 엔진의 해당 암호화 방식 지원 여부를 먼저 확인한다. 엔진 미연결이나 미구현을 암호 오류로 안내하거나 입력창을 반복 표시하지 않는다.
- 목록이 공개된 파일은 목록을 먼저 표시하고, 암호가 필요한 항목에 접근할 때 입력창을 연다.
- 헤더와 파일명이 암호화된 파일은 목록을 읽기 전에 암호를 요청한다.
- 암호 입력 취소는 앱 종료나 무한 재요청으로 이어지지 않아야 한다.
- 암호는 기본적으로 저장하지 않으며 현재 파일을 다루는 세션 범위에서만 유지한다.
- 암호를 로그, 명령행 인자, 환경변수와 영구 설정에 남기지 않는 연동 방식을 선택한다.
- 암호 응답은 작업 ID와 요청 ID에 연결하고 취소, 종료와 요청 만료 후의 응답을 다른 작업에 재사용하지 않는다. 암호 객체의 소유권과 폐기 책임을 어댑터 계약에 명시한다.
- 암호 오류와 손상을 구분할 근거가 부족하면 한쪽으로 단정하지 않고 확인 가능한 상태를 안내한다.

## 6. 암호화 파일과 미리보기

파일 목록의 열람과 파일 내용의 미리보기를 구분한다. 암호화된 내용 자체는 올바른 암호 없이 미리볼 수 없다.

| 상태 | 암호 입력 전 | 암호 입력 후 |
| --- | --- | --- |
| 목록과 내용이 공개됨 | 목록과 지원 항목 미리보기 | 별도 입력 불필요 |
| 목록은 공개되고 내용은 암호화됨 | 목록 표시, 암호화된 내용에는 잠금 상태 표시 | 지원 항목 미리보기 |
| 일반 파일과 암호화 파일이 섞임 | 공개된 목록과 일반 파일 미리보기 | 암호화된 지원 항목도 미리보기 |
| 헤더와 파일명까지 암호화됨 | 암호 입력창 표시 | 목록과 지원 항목 미리보기 |

초기 미리보기는 일반 텍스트와 검증된 래스터 이미지부터 제공하는 안으로 검토한다. 허용 확장자와 실제 콘텐츠 형식을 함께 확인한다. PDF와 오피스 문서는 별도 렌더러의 크기와 처리 비용을 검토한 뒤 추가한다.

- 사용자가 선택한 항목만 처리하며 전체 파일을 미리 해제하지 않는다.
- 미리보기 처리 용량, 이미지 해상도, 시간과 메모리에 제한을 둔다.
- 솔리드 압축처럼 선택 항목 접근에도 선행 데이터 처리가 필요한 경우 진행 상태와 취소를 제공한다.
- 미리보기에서 실행파일, 스크립트, 문서 매크로를 실행하지 않는다.
- 자동 외부 앱 실행과 외부 리소스 요청을 차단한다. HTML과 SVG 같은 활성 콘텐츠를 초기 래스터 이미지 허용 목록으로 취급하지 않는다.
- 임시 파일이 필요하면 접근 범위와 수명을 제한하고 정상 종료 및 다음 실행 시 잔여 파일 정리를 고려한다.
- 임시 데이터 정리를 저장장치에서의 완전 삭제 보장으로 설명하지 않는다.

## 7. 손상 파일 자동 복구

복구의 목표는 남아 있는 정보를 이용해 열람과 추출 가능성을 높이는 것이다. 유실된 데이터를 항상 복원하거나 모든 형식의 손상을 고칠 수 있다고 보장하지 않는다.

정상 열기 시도 → 형식과 손상 상태 확인 → 제한된 자동 복구 시도 → 열람 가능한 목록 표시 → 결과 검증 → 별도 저장

| 손상 또는 오류 유형 | 처리 계획 |
| --- | --- |
| 확장자와 실제 형식 불일치 | 제외 정책 확인 후 실제 형식으로 열기 시도 |
| ZIP의 목록 정보 손상 | 남아 있는 개별 파일 헤더를 이용한 목록 재구성 검토 |
| 일부 항목 데이터 손상 | 정상 항목을 분리하고 읽을 수 있는 항목만 추출 |
| 분할 파일 누락 | 필요한 조각의 이름을 안내하고 완전 복구로 표시하지 않음 |
| 7Z의 헤더 손상 | 남은 구조로 가능한 범위를 진단하고 검증된 유형부터 확대 |
| 압축 데이터나 메타데이터 유실 | 부분 복구 또는 복구 불가로 안내 |

- 원본 파일을 직접 수정하지 않는다. 복구가 필요하면 메모리상의 정보나 별도 작업 사본을 사용한다.
- 자동 진단과 복구에는 자원 제한과 취소를 제공한다. 범위를 넘는 정밀 작업은 사용자가 선택하게 한다.
- 목록이 열린 사실과 파일 내용이 정상이라는 사실을 구분한다.
- 엔진이 제공하는 CRC나 인증 검증을 활용하고, 추출 여부와 무결성 검증 여부를 따로 기록한다.
- 결과는 "정상", "일부 복구", "검증 불가", "복구 불가"로 구분한다.
- 복구한 파일명이나 폴더 구조를 추정했다면 원래 정보와 구분해 표시한다.
- 심하게 손상된 항목도 정상 파일처럼 자동 실행하거나 열지 않는다.

ZIP 복구를 초기 대상으로 제안한다. 7Z와 RAR의 복잡한 복구는 엔진 기능, 형식 구조, 라이선스와 손상 샘플을 검증한 뒤 확대한다. 메타데이터나 압축 데이터가 없는 경우의 완전 복구는 수용 기준으로 삼지 않는다.

## 8. 다운로드와 설치 경험

### README 상단

다른 안내보다 먼저 다음 순서로 배치한다.

1. 큰 제목 "Zipelo"
2. "쉽고 빠른 압축과 압축 해제 프로그램"이라는 간단한 소개
3. "Windows용 다운로드"라고 명확히 적힌 큰 다운로드 버튼 이미지와 링크
4. "다운로드한 파일을 더블클릭하고 [설치]를 누르세요"라는 Windows용 짧은 안내

Ubuntu 24.04/26.04 LTS x64용 다운로드도 별도로 식별할 수 있게 준비한다. 해당 패키지가 각 LTS에서 검증되기 전에는 준비 중으로 표시한다. Windows 설치 파일을 Ubuntu용으로 제공하지 않는다. Ubuntu의 GUI 패키지 설치 흐름과 필요한 시스템 의존성은 실제 환경에서 검증한 안내를 사용한다.

주요 버튼은 최신 안정 버전 설치 파일을 직접 다운로드하는 링크로 구성한다. 포터블과 다른 아키텍처는 보조 링크로 구분한다. GitHub에서 지원되는 이미지 링크를 사용하고 임의의 스크립트나 CSS에 의존하지 않는다.

설치 파일명을 `Zipelo-Setup-x64.exe`처럼 고정하면 다음 경로를 사용할 수 있다.

```text
https://github.com/Team-LJY/zipelo/releases/latest/download/Zipelo-Setup-x64.exe
```

위 경로는 계획된 배포 주소이며 현재 다운로드 가능함을 의미하지 않는다. 파일 게시와 검증이 완료된 후 실제 다운로드 버튼으로 활성화한다. 일반 사용자의 로그인 없는 다운로드를 위해 공개 배포 경로가 필요하며 저장소 공개나 릴리스 게시는 별도 승인 후 진행한다.

현재 README는 제목, 소개와 큰 "다운로드 준비 중" 이미지를 제공한다. 설치 파일이 없음을 명시하며 이미지는 다운로드 링크가 아니다. 준비 상태와 실제 다운로드 가능한 상태를 구분한다. 이번 안내 검토에서도 README의 "설치 파일은 아직 없습니다"와 다운로드 링크가 아니라는 표시를 확인했다. 개발용 build/publish 안내는 일반 사용자용 설치 경로가 아니며 Windows/Ubuntu 설치 파일이 이미 배포됐다는 의미로 사용하지 않는다.

### 설치 흐름

설치 파일 더블클릭 → [설치] → 진행 상태 → 설치 완료 → [기본 앱 설정] 또는 [나중에]

- 기본 경로와 옵션으로 설치할 수 있게 하고 세부 설정은 보조 선택으로 둔다.
- 사용자 단위 설치를 우선 검토해 불필요한 관리자 권한 요청을 줄인다.
- 일반 사용자에게 .NET SDK 설치나 소스 빌드를 요구하지 않는다. 런타임을 포함하는 배포와 OS 패키지 관리자의 명시된 의존성 처리를 검토한다. 개발용 작업자 배치와 최종 설치 패키지는 구분한다.
- 오프라인 설치 가능 여부를 검증하고 추가 다운로드가 필요하면 이를 명시한다.
- 실패 시 이유와 재시도 방법을 제공하고 불완전한 설치를 성공으로 표시하지 않는다.
- 배포 파일 서명과 체크섬 제공을 검토한다. 서명이 보안 경고 제거를 보장하지는 않는다.

### 기본 앱 연결

Windows의 기본 앱 변경은 지원되는 시스템 UI를 통한 사용자 선택을 따른다. Zipelo의 버튼 한 번으로 모든 압축 확장자를 즉시 강제 변경하는 동작은 요구사항으로 확정하지 않는다.

- 설치 시 지원 형식의 처리 앱으로 Zipelo를 등록한다.
- 설치 완료 화면에서 기본 앱 변경 의사를 묻고 Windows의 해당 설정 화면으로 안내한다.
- JAR와 제외 대상으로 확정된 컨테이너 형식은 연결 목록에서 제외한다.
- 설정 후 확인 가능한 연결 상태를 보여주고 단순한 설정 화면 진입을 적용 완료로 표시하지 않는다.
- [나중에]를 선택해도 바로 사용할 수 있게 하고 반복적으로 변경을 강요하지 않는다.
- 업데이트가 사용자의 기본 앱 선택을 임의로 변경하지 않도록 한다.

Ubuntu는 .deb 패키지, 데스크톱 항목과 MIME 처리 앱 등록을 준비한다. JAR와 제외 확정 형식은 패키지 등록과 앱 진입 모두에서 제외하며, 설치와 업데이트가 사용자 동의 없이 기본 앱을 변경하지 않는다. 등록, 기본 앱 변경 동의, 실제 적용 결과를 구분한다. 상세 수용 기준은 [플랫폼 지원 계획](PLATFORM_SUPPORT.md)을 따른다.

## 9. 경량성과 성능 목표

네이티브 UI와 검증된 압축 엔진을 조합하는 구성을 우선 검토한다. UI와 압축 작업은 별도 프로세스로 분리해 작업 실패가 화면 응답성에 미치는 영향을 줄이는 안을 제안한다. 별도 프로세스만으로 보안 격리가 완료되는 것은 아니므로 실행 권한과 자원 제한도 검토한다.

| 항목 | 초기 목표안 | 측정 조건 |
| --- | --- | --- |
| 설치 파일 크기 | 30MB 이하 | 필수 구성요소를 포함한 배포물 |
| 유휴 메모리 | 80MB 이하 | 작업이 없는 초기 화면의 전체 프로세스 합산 |
| 초기 화면 표시 | 콜드 실행 2초 이내 | 합의한 기준 PC와 저장장치에서 측정 |
| 압축과 해제 시간 | 같은 엔진 대비 추가 비용 15% 이내 | 같은 입력, 엔진 버전, 설정과 검증 범위 |

수치는 측정 전 제안이며 확정 성능이나 일정 약속이 아니다. 기준 PC, 반복 횟수, 캐시 상태와 집계 방식을 먼저 정한 뒤 결과로 조정한다.

현재 UI의 WPF 선택과 Windows x64 자체 포함 배포 프로필은 소스 수준의 개발 선택이다. 런타임을 포함한 실제 배포 크기를 측정하지 않았으므로 30MB 목표를 달성했다고 표시하지 않는다. 배포 편의성과 크기가 충돌하면 측정 결과와 대안을 비교해 목표를 조정한다.

압축 가능한 대용량 파일, 이미 압축된 파일, 작은 파일 다수, 암호화 파일, 솔리드 파일을 구분해 측정한다. 복구와 미리보기는 정상 해제와 분리해 측정한다. 처리 시간과 함께 최대 메모리, CPU 사용량, 디스크 사용량, 취소 반응과 결과 무결성을 확인한다.

같은 엔진 버전, 입력, 사전 크기, 스레드 수, 암호와 검증 설정을 고정한다. 콜드 실행과 캐시가 있는 실행을 분리하고 조건별 최소 5회 측정해 중앙값과 범위를 기록하는 안으로 검토한다.

작업 중 메모리는 압축 사전 크기와 동시 작업 수 등에 영향을 받으므로 유휴 메모리 목표와 구분한다. 처리량을 위해 자원 제한을 무조건 해제하지 않는다.

## 10. 데이터 보호와 오류 처리

- 추출 경로를 정규화하고 상위 폴더 이동, 절대 경로, 링크를 이용한 목적지 밖 쓰기를 방지한다.
- Windows의 드라이브 상대 경로, UNC, 장치 경로, 대체 데이터 스트림, 예약 이름과 정규화 충돌을 검사한다. Ubuntu의 합법적 파일명을 Windows 규칙으로 무조건 거부하거나 대소문자가 다른 항목을 조용히 합치지 않는다. 경로 구분, 이름 비교와 충돌은 대상 OS 및 파일시스템 정책으로 분리한다. 문자열 검사와 실제 파일 생성 시의 목적지 검증을 구분한다.
- 초기에는 압축 내부 심볼릭 링크와 하드 링크를 거부하는 정책을 검토한다. Windows 링크와 junction, Ubuntu symlink 및 양쪽 OS의 경로 교체 경쟁은 실제 저장 계층에서 각각 방어하고 검증해야 한다.
- 메모리 ZIP을 사용자가 고른 새 파일에 게시하는 기능은 임의 항목 해제와 별개로 검증한다. 기존 파일을 덮어쓰지 않고 입력을 보존하며 실패와 취소의 임시 파일, 부분 결과 및 게시 이후 늦은 취소를 명확히 처리한다. 안전 조건을 갖추지 못한 해제는 비활성으로 유지한다.
- 비정상적으로 큰 해제 용량, 파일 개수와 중첩 깊이에 대한 제한을 설계한다.
- 헤더 선언값뿐 아니라 실제 처리량과 출력량을 작업별로 누적한다. 중간 TAR, 솔리드 선행 처리, 미리보기와 복구 재시도에서도 누적 예산을 초기화하지 않는다. 하위 작업 제한을 별도로 두더라도 전체 예산을 함께 적용한다.
- 시간, 메모리와 CPU의 강제 제한은 협력적 취소와 구분한다. 현재 작업자는 취소와 시간 초과 시 종료를 시도하고 종료를 확인하는 경계를 제공하지만, OS별 강제 메모리 및 CPU 제한이나 보안 샌드박스가 구현됐다는 뜻은 아니다. Windows와 각 Ubuntu LTS에서 실제 종료 및 자원 제한을 따로 검증한다.
- 기존 파일 덮어쓰기는 사용자가 선택한 정책에 따른다.
- 디스크 부족, 읽기 및 쓰기 권한 오류, 작업 취소와 엔진 실패를 구분한다.
- 진단 정보에는 암호나 파일 내용을 기록하지 않고 경로와 파일명 같은 개인정보 노출도 최소화한다.
- 미완성 출력과 검증에 실패한 출력은 정상 결과와 구분한다.

## 11. MIT 라이선스와 외부 구성요소

Zipelo 자체 작성 코드의 라이선스는 MIT로 확정한다. 상업적 이용, 회사 내부 사용, 수정과 재배포를 허용한다. MIT는 저작권 및 허가 고지 유지 등의 조건을 두며 수정본 소스 공개를 강제하지 않는다.

외부 코드는 각자의 라이선스를 유지한다. MIT를 선택했다는 이유로 포함된 엔진과 라이브러리를 MIT로 다시 표시하지 않는다.

비상업 조건을 철회한 결정은 유지하며 다시 확인받지 않는다. 용도 제한이 있는 코드가 포함되는지는 자체 코드의 MIT 표기와 별개로 검토한다. 전체 엔진을 그대로 포함하거나 참고용 코드를 복사해 사용하기 전에 실제 배포 대상 코드의 출처와 권리 관계를 확인한다.

- 자체 코드와 문서의 루트 [LICENSE](../LICENSE)는 표준 MIT 본문과 `Copyright (c) 2026 Team-LJY contributors` 귀속을 사용한다. 제3자 구성요소의 라이선스와 저작권 고지는 각 원문을 유지하며 이 LICENSE로 대체하지 않는다. 실제 배포물의 별도 고지는 추가 준비가 필요하다.

- 엔진 수정과 연결 방식에 따라 소스 제공, 교체 가능성 등의 의무를 검토한다.

### 작업 순서와 공통 계약

1. 현재 체크아웃과 변경 소유자를 확인하고 사용할 도구, 실행 가능한 검사와 환경 제약을 기록한다. 공유 작업 중에는 임의로 브랜치를 전환하지 않는다.
2. 프론트엔드와 백엔드가 작업 ID, 항목 ID, 이벤트 순번, 암호 요청과 응답, 취소, 오류와 항목별 검증 상태의 의미를 합의한다. 기존 UI 경계와 코어 계약을 같다고 가정하지 않는다.
3. 엔진 독립 기반과 UI 상태, 테스트 구조를 담당 범위에서 작성한다. 독립 작업은 파일과 공용 자원의 충돌이 없는지 확인한 뒤 진행한다. 가짜 엔진 결과는 제품 기능으로 제공하지 않는다.
4. 후보의 기능과 출처 및 라이선스 검증을 진행하고 실제 어댑터, 안전한 저장 계층, 작업 프로세스와 UI 연결을 구현한다. 필요한 도구 설치나 접근 권한이 없으면 정확한 제약을 보고한다.
5. 코어 실행과 경계값 회귀 검사, 형식별 실제 엔진 샘플, OS별 링크와 경로 보호, UI 및 설치를 검증한다. Windows 결과를 Ubuntu 결과로 대체하지 않으며 Ubuntu 준비를 Windows 전체 완료에 종속시키지 않는다. 미실행 검사는 통과로 계산하지 않는다.
6. 배포물과 소스의 대응, 고지와 서명, 다운로드 경로와 설치 흐름을 확인한 뒤 공개 전 승인 조건을 확인한다.

공통 계약은 엔진 종류에 독립적이어야 한다. 최소한 다음 의미를 보존한다.

- 작업 상태는 실행, 암호 대기, 취소 요청, 취소 완료, 실패, 부분 완료와 정상 완료를 구분한다. 늦게 도착한 다른 작업의 이벤트를 현재 화면에 적용하지 않는다.
- 암호 응답은 요청 ID와 현재 작업에만 유효하며 취소와 제한 횟수를 존중한다. UI에서 코어로 넘길 때 객체의 소유권과 폐기 시점을 합의한다.
- 임시 출력 생성과 최종 게시를 구분한다. 경로 검사만으로 실제 출력 저장 계층의 안전성을 보장하지 않는다.
- 항목의 추출 상태와 CRC 또는 인증 검증 상태를 따로 전달한다. 검증하지 않았거나 검증할 수 없는 결과를 정상 검증 완료로 표시하지 않는다.
- 엔진, 저장 계층이나 기능이 없으면 사용 불가 상태와 오류를 반환한다. 실제 엔진 없이 압축 완료를 표시하지 않는다.

계획 담당 범위는 이 문서와 플랫폼 지원 계획, 자체 코드의 루트 LICENSE다. 구현과 검증 파일은 해당 역할 담당자가 관리한다. 공유 작업 폴더의 브랜치, 인덱스와 다른 담당자의 파일을 임의로 변경하지 않는다.

### 브랜치 규칙과 초기 기준점

프로젝트 공통 작업 지침의 첫 항목은 다음과 같다.

> Follow the established web-usta GitHub branch structure: features/* for feature work, fix/* for bug fixes, and docs/* for documentation. Use a descriptive task branch with the appropriate prefix. For other categories, check the repository's existing documented convention rather than inventing a prefix.

기능은 `features/*`, 결함 수정은 `fix/*`, 문서는 `docs/*`를 사용한다. 다른 분류의 접두어나 추가 계층은 근거 없이 만들지 않는다. 커밋 메시지는 간결한 한국어로 작성한다.

2026-11-09 원격 main의 초기 기준점은 `ee7638591d18877e0564f6748fb9036ec2b6092d`이며 `.gitignore`만 포함한다. 기획 문서와 MIT LICENSE는 이 기준점의 `docs/initial-project-plan` 브랜치에서 분리한다. 공유 폴더에서 일괄 스테이징, 커밋이나 checkout을 수행하지 않고 명시적인 담당 파일 목록만 원격 브랜치에 반영한다.

기존 읽기 조사에서 저장소는 커밋이 없었으나 이후 초기 main이 생성됐다. 과거 빈 저장소 결과를 현재 상태로 사용하지 않는다. 새 main의 branch 조회에는 `protected=false`가 표시됐지만 별도 protection 및 조직 상속 rulesets 상세 조회는 403으로 제한됐다. 모든 조직 정책이 없다고 단정하지 않으며 보호규칙 우회, 권한 확대나 공개 설정 변경은 작업에 포함하지 않는다.

계정 인증과 Git 작성자 정보는 구분한다. 각 담당자는 지정된 연결로 본인의 인증 사용자 및 저장소 권한을 확인하고 담당 브랜치만 사용한다. main 병합과 충돌 조율은 총괄이 맡는다. 릴리스 파일 업로드, 공개 배포, 결제, 추가 설치와 권한 변경은 별도 범위로 유지한다.

### 기능별 분리 검토안

아래는 현재 파일의 역할과 의존성을 기준으로 한 분리안이다. 초기 main에는 제품 소스 이력이 없고 일부 로컬 파일에 여러 기능이 합쳐져 있으므로 과거 기능별 패치를 자동 복구할 수 있다고 가정하지 않는다. 구현 브랜치의 실제 파일 경계와 순서는 소유자 및 총괄이 확정한다.

- 공통 계약과 기본 ZIP 작업자: `src/Zipelo.Core/`, `src/Zipelo.Runtime/`, `src/Zipelo.Worker/` 및 대응 회귀 검사와 기술 문서를 기능 단위로 묶는다. 이후 게시와 해제가 같은 파일을 변경하므로 백엔드 소유자가 경계를 먼저 정해야 한다.
- 새 ZIP 파일 게시와 Windows 수정: `NewZipPublisher` 및 OS별 게시 구현과 `tests/runtime/PublicationTests.cs`를 연동한다. 신규 게시 기능은 `features/*`, 그 위의 독립 결함 수정은 `fix/*`로 구분하는 안이며 기준 커밋이 먼저 필요하다.
- Windows UI와 Ubuntu UI: 각 프로젝트를 구분하되 Ubuntu가 링크하는 `ZipCreationWorkflow.cs` 및 시작 인수 계약은 선행 공통 UI 변경으로 묶거나 소유자 간 반영 순서를 합의한다. 검증 빌드 설정을 일반 배포 설정으로 바꾸지 않는다.
- 시작 인수 및 설치 초안: `docs/LOCAL_ARCHIVE_OPEN.md`와 UI 인수 처리, `packaging/`의 진입 명령 및 manifest가 같은 계약을 사용해야 한다. 설치 초안은 실제 설치/연결 검증과 구분한다.
- 비암호화 ZIP 메모리 해제와 새 폴더 게시: 공유 Runtime/Worker 변경 및 `tests/extraction/`을 기존 검증된 게시 범위와 구분한다. 현재 새 폴더 게시의 실패 폐쇄와 미실행 검사를 유지한다.
- 계획과 플랫폼 상태: `docs/PLANS.md`, `docs/PLATFORM_SUPPORT.md`는 `docs/*` 작업 후보로 묶는다. 다른 담당자의 기술 문서는 해당 구현 변경과 함께 소유자가 확인한다. README와 다운로드 자산은 UI/안내 소유 범위를 보존한다.

테스트는 해당 기능 또는 결함 수정과 함께 루트 `tests/` 안의 파일만 포함한다. 근거 없는 tests/* 접두어를 만들지 않는다. 파일 해시와 선행 계약을 고정해 검토하며, 이 문서 브랜치에는 `docs/PLANS.md`, `docs/PLATFORM_SUPPORT.md`, `LICENSE`만 추가한다. 다른 구현과 검증 파일은 해당 브랜치의 의존 산출물로 별도 관리한다.

## 14. 실제 구현과 검증 상태

다음은 2026-11-09의 로컬 소스 열람과 담당자 보고를 구분한 기록이다. 기획 담당자는 이번 문서 갱신에서 제품 빌드, C# 실행이나 Windows/Ubuntu GUI 및 설치 검사를 하지 않았다. 공유 소스의 후속 수정은 아래 고정 Windows 스냅샷에 자동 포함되지 않는다.

### 로컬 소스에서 확인한 구현

- Windows Desktop은 .NET 10 WPF이며 Core/Runtime 어댑터와 작업자 기반 ZIP 목록, 생성 및 단일 새 파일 게시 연결이 작성됐다. Ubuntu UI도 별도 프로젝트에 작성됐지만 실제 LTS 빌드와 실행 검증은 남아 있다.
- 두 UI가 공유하는 생성 워크플로는 bounded read 후 `writable:false` 스트림을 전달하도록 수정됐다. 이번에 읽은 `ZipCreationWorkflow.cs` SHA-256은 `1529b854f31bfb321bbdfeff97cdb1e5d69ac00281873ce881ffea3dc013789f`로 전달된 수정 파일과 일치한다. 파일 일치는 전체 최신 UI 재검증을 뜻하지 않는다. 일반 Debug/Release 생성은 비활성이고 명시적 개발 검증 빌드에서만 허용한다.
- Core/Runtime/Worker에는 OS별 파일명과 대소문자 정책, 작업자 실행 경계, 예산 및 단일 새 ZIP 게시 API가 있다. 최신 Windows 게시 관련 실행 근거는 아래 round5 결과로 갱신한다. Ubuntu 안전 게시 검증은 별도다.
- 비암호화 ZIP의 작업자 메모리 해제와 경로/타입/중복, 실제 해제량, CRC/길이 대조 코드가 추가됐다. 해제 계약 (`docs/ZIP_EXTRACTION.md`, 별도 구현/검증 브랜치)의 소스 존재와 실행 검증을 구분한다. `NewFolderPublisher.IsSupportedPlatform=false`이며 Windows/Linux 모두 공개 폴더 게시가 실패 폐쇄 상태다. 일반 UI 해제 capability도 비활성이다.
- `packaging/`에 Windows 사용자 범위 설치와 Ubuntu .deb/desktop/MIME 초안 및 manifest 기반 차단 검사가 작성됐다. 실제 설치 패키지 생성, 설치/업데이트/제거, 서명이나 공개 결과가 아니다. 시작 인수 처리도 소스가 작성됐으나 실제 OS 검증 전에는 연결 등록 차단을 유지한다.
- README는 설치 파일 없음과 다운로드 준비 표시이며 실제 다운로드 링크가 아니다. 외부 엔진 채택과 전체 형식/암호/복구 요구는 미완료로 유지한다.

### 최신 전달된 Windows 실행 결과

다음은 프로젝트 검증 담당자의 결과를 총괄이 전달한 보고다. 기획 담당자가 VM이나 테스트를 직접 실행한 결과가 아니다. 정확한 기준을 모르는 결과에는 새 스냅샷 식별자를 추정해 붙이지 않는다.

- Windows round5 C# 62개 전부 통과가 전달됐다. Desktop/Core/Runtime/Worker 빌드는 경고 0, 오류 0으로 보고됐다. 새 ZIP 파일 저장/내용 일치, 기존 파일 및 입력 충돌 보존, 부모/최종 symlink 거절의 실행 근거다.
- 이후 공유 생성 스트림 수정이 반영된 개발 검증 UI에서 실제 생성, 충돌 시 기존 파일 보존, 파일 선택 취소 후 재시도 성공이 전달됐다. 해당 Windows UI 흐름의 근거이며 최신 시작 인수 처리나 새 해제 기능까지 검증한 결과는 아니다.
- 이번 전달에는 round5의 정확한 스냅샷 시각과 전체 파일 해시, UI 재검증 전체 파일 목록이 없다. 소스가 더 바뀐 현재 체크아웃 전체의 통과로 일반화하지 않는다.
- 과거 2026-11-09T13:59:27.796888Z의 57/60과 게시 관련 3개 실패는 이전 결과다. 해당 게시 회귀는 후속 62개 통과로 갱신됐으며 현재 미해결 게시 실패 3개로 계속 표시하지 않는다. 앞선 39개 통과도 과거 범위에만 해당한다.

### round6의 별도 실행 결과

2026-11-09T14:44:04.604469Z의 src/tests 102개 독립 스냅샷에 대한 후속 보고다. Desktop/Core/Runtime/Worker 빌드는 경고 0, 오류 0이며 Core 41개는 통과했다. RuntimeTests는 당시 `tests/runtime/ExtractionPublicationTests.cs(125,22)`의 CS0266, `FileSystemInfo`를 `DirectoryInfo`로 암시 변환할 수 없는 오류로 컴파일에 실패했다. 따라서 Runtime 56개는 전부 미실행이다.

이는 round5의 기존 62개 통과를 소급 취소하는 결과도, 신규 97개 전체의 통과도 아니다. 해당 타입 오류를 최소 수정한 뒤 같은 고정 스냅샷에서 재실행해야 한다. 원본에서 병행 중인 새 폴더 게시 구현을 이 결과에 섞지 않는다. 이후 패치나 재실행 결과가 확인되기 전에는 성공으로 갱신하지 않는다.

### 새 해제 및 Ubuntu와 배포 미검증

- 검증 담당자의 해제 검사 기록 (`tests/extraction/coverage.json`, 별도 구현/검증 브랜치)은 기존 62개에 새 해제 검사 35개를 더해 총 97개 등록을 기록한다. 새 35개의 C# 컴파일과 실행은 로컬 SDK 부재로 미실행이다. 폴더 게시의 수용 검사 8개는 현재 기능 게이트로 차단돼 있으며 통과로 계산하지 않는다. Windows 62개 통과가 신규 97개 통과라는 뜻은 아니다.
- 같은 로컬 기록의 Python 33개 통과는 샘플과 정적 검사 범위이며 C# 해제, 실제 OS 저장이나 UI 실행의 대체 근거가 아니다. 이번 기획 작업에서 제품 검사를 재실행하지 않았다.
- Ubuntu 24.04 LTS x64와 26.04 LTS x64의 UI, 실제 기능, 네이티브 안전 게시 및 설치 검증은 미완료다. 현재 호스트가 Ubuntu 26.04.1 LTS인 사실과 전달된 GNOME Wayland/XWayland 정보는 앱 실행 증거가 아니다. 다른 아키텍처도 미검증이다.

[플랫폼 지원 계획](PLATFORM_SUPPORT.md), OS별 테스트 행렬 (`tests/security/platform_matrix.json`, 별도 구현/검증 브랜치) 및 담당 기술 기록을 함께 읽는다. 단일 ZIP 저장의 Windows 실행 성공과 새 폴더로의 안전한 해제 저장은 다른 범위다. 후자는 외부 항목 삽입과 경로 교체/정리 조건 및 실제 OS 검증이 해결될 때까지 실패 폐쇄를 유지한다. 일반 사용자용 생성 활성화, SDK 없는 설치와 업데이트/제거, 기본 연결 및 전체 제품 요구는 별도 조건이다. 개발 검증 통과가 일반 배포 완료나 공개 승인으로 바뀌지는 않는다.
