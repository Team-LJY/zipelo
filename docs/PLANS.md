# Zipelo 기획서 (v0.1 및 v0.2 계획)

누구나 쉽게 설치해 쓰는 가볍고 빠른 MIT 오픈소스 압축 프로그램을 만든다. 1~7절은 첫 출시판(v0.1)의 범위와 완료 기준이며, 8절은 이후 한계를 개선할 v0.2 계획이다. 요구사항은 구현이나 검증 완료를 뜻하지 않는다.

## 1. 확정된 결정

- 기술 스택은 Rust 하나로 한다. C# 구현은 중단했으며, 로컬 백업 후 PR103(f1d9fa5)에서 소스와 전용 시험 및 .NET 설정을 제거했다. C# 재개는 v0.1 이후 계획에도 포함하지 않는다.
- 압축 처리는 별도 작업자 프로세스에서 한다. 앱(UI)은 작업자와 요청/응답 메시지로 통신한다.
- v0.1에서는 외부 라이브러리를 최소화하고 압축 형식을 직접 구현하는 방침을 사용했다. v0.2의 라이브러리 허용 기준은 8.13절을 따른다.
- 예외: AES 암호화와 암호 해시는 RustCrypto(MIT/Apache, 순수 Rust)를 쓴다. 해제용 zlib-rs(Zlib 라이선스), UI의 eframe wgpu와 운영체제 기본 파일 창용 rfd도 승인된 예외로 사용한다.
- RAR는 라이선스 문제로 v0.1에서 제외한다.
- 설치 마지막 단계의 [적용]은 Zipelo를 연결 프로그램으로 등록하고 Windows 기본 앱 설정 화면을 연다. Windows는 앱이 기본 프로그램을 강제로 바꾸지 못하게 막는다. Ubuntu는 바로 적용한다.
- 자체 코드는 MIT 라이선스다.
- 화면은 main의 experiments/rust-ui-memory-app을 기준으로 한다.

## 2. v0.1 범위

포함:

- 해제: ZIP(Store/Deflate), TAR, GZ, TAR.GZ. 이어서 7z(LZMA).
- 생성: ZIP.
- 암호가 필요한 압축파일이면 작업자가 앱에 암호 요청을 보내고 암호 입력창을 띄운다. 암호 ZIP 생성과 해제는 완료 기준에 포함한다.
- 파일 더블클릭 또는 끌어다 놓기로 열기, 목록 보기, 풀기, ZIP 만들기, 진행률과 취소.
- 안전한 해제: 지정 폴더 밖에 쓰지 않고 기존 파일을 덮어쓰지 않는다. 압축 폭탄과 틀린 암호를 안전하게 처리한다.
- 배포: Windows x64 설치 파일, Ubuntu .deb, README 다운로드 버튼, 설치 마지막의 기본 앱 설정 단계.

보류(v0.1 이후):

- RAR, 손상 파일 복구, 미리보기, 분할 압축, 7z 생성, TAR.BZ2/XZ.
- JAR와 앱/문서용 컨테이너는 계속 지원 대상과 기본 연결 대상에서 제외한다.

## 3. 아키텍처

- 앱: Rust(eframe) 화면. 압축 파싱을 앱에서 직접 하지 않는다.
- 작업자: 별도 Rust 실행 파일. 목록, 해제, ZIP 생성, 암호 요청, 취소를 처리하고 진행, 완료, 실패 이벤트를 보낸다.
- 통신 형식은 backend와 frontend 담당이 합의한 계약을 따른다. 작업 ID, 취소 후 종료 확인, 부분 출력 보고를 포함한다.
- 실제 구현은 experiments/rust-ui-memory-app과 experiments/rust-archive-worker를 기준으로 한다. UI 및 작업자 시험은 tests/ 아래에 둔다.

## 4. 담당과 검증 기준

- backend는 Rust 작업자와 압축 처리, frontend는 Rust 앱과 UI, bugfix는 결함 검토와 회귀 검증, planning은 요구사항과 문서를 담당한다.
- 현재 기능과 알려진 한계는 [릴리스 노트](release-notes-v0.1.md), 화면 동작은 [UI 설계](ui-design-v0.1.md)를 따른다. 과거 C# 시험 수와 미구현 상태를 현재 Rust 상태로 재사용하지 않는다.
- 빌드와 시험은 로컬에서 `python3 tests/ci/run_rust.py local`로 돌리고 결과를 PR 본문에 적는다. GitHub Actions는 수동 실행 Windows 확인용만 쓴다.
- 작업 사본, 빌드 캐시와 임시 파일은 프로젝트의 tests/work/ 아래에 둔다. 각 플랫폼의 실제 실행과 릴리스 게시 여부는 빌드 통과와 별도로 확인한다.

## 5. 완료 기준

- 새 PC에서 설치 파일을 더블클릭해 설치하고 기본 앱 단계까지 진행된다.
- zip, 7z, tar.gz를 더블클릭해 열고 풀 수 있다.
- 암호 ZIP을 만들고 풀 수 있다.
- Linux 시험과 Windows 교차 빌드가 로컬 실행기로 통과한다. Windows 실제 실행은 출시 전에 수동으로 확인한다.
- 폴더 밖 경로, 압축 폭탄, 틀린 암호 회귀 시험이 통과한다.
- 지원하지 않는 형식을 지원한다고 안내하지 않는다. 실제 검증 전에는 지원 완료로 표시하지 않는다.

## 6. 승인이 필요한 항목

- 릴리스 게시, 서명 인증서 같은 비용, 공개 설정 변경은 이준영 님 승인 후 진행한다.
- v0.1에서는 위 예외 외 새 라이브러리에 사전 확인이 필요했다. v0.2에서는 8.13절의 허용 기준을 따르며 그 밖의 의존성은 사전 확인을 받는다.

## 7. C# 중단과 과거 검증 기록

C# 코드는 v0.1의 빌드, 실행과 배포에 사용하지 않는다. 삭제 전 소스는 git 이력의 `ae91536`에서 확인할 수 있고, linux-desktop-2의 `tests/work/archive/csharp-backup-ae91536/`에도 백업되어 있다. 과거 C# 문서는 설계 및 검증 이력으로 보존하며, 그 문서의 명령을 현재 main의 개발 절차로 사용하지 않는다. .NET SDK, WPF와 Avalonia는 현재 제품을 빌드하기 위한 요구사항이 아니다.

다음 두 정적 검사는 C# 파일 해시를 고정한 과거 기준 검사다.

- `tests/rust-memory-ustar-reader/static_check.py`
- `tests/rust-memory-gzip-reader/static_check.py`

C# 제거 뒤 main에서는 삭제된 경로를 읽다가 실패한다. 이 검사는 정식 검증 `tests/ci/run_rust.py local`과 패키징의 실행 대상이 아니며, 남아 있는 실패를 현재 검사 통과로 표시하지 않는다. 검사와 연결된 해시 기록은 변경하지 않고 보존한다.

당시 결과를 재확인하려면 현재 작업 공간을 되돌리지 말고 `ae91536`의 별도 작업 사본을 프로젝트의 `tests/work/` 아래에 준비한 뒤 그 사본의 루트에서 실행한다. `ae91536`은 지정한 C# 제거 전 재현 스냅샷이며, 각 검사의 계약과 SHA256SUMS도 같은 스냅샷을 사용한다.

```bash
python3 -B tests/rust-memory-ustar-reader/static_check.py
python3 -B tests/rust-memory-gzip-reader/static_check.py \
    --source-head e1ffd7bbffc358b6e53358682a93bf3ce075e892 \
    --test-manifest-sha256 "$(sha256sum tests/rust-memory-gzip-reader/SHA256SUMS | cut -d ' ' -f 1)"
```

이 재현은 과거 정적 기록의 확인이며 현재 Rust 제품의 빌드, 실행 또는 출시 검증을 대신하지 않는다.

## 8. v0.2 한계 개선 계획

2026-11-13의 사용자 지시에 따라 [README](../README.md)와 [v0.1 릴리스 노트](release-notes-v0.1.md)의 한계를 개선 대상으로 관리한다. 아래 방법과 수용 기준은 계획안이며, 해결됨 항목은 main 반영을 뜻하고 릴리스 배포 완료를 뜻하지 않는다. v0.1의 제외 항목은 과거 범위로 유지한다. JAR와 앱/문서용 컨테이너 제외는 의도한 제품 범위이므로 이번 개선에 넣지 않는다.

우선순위 P1은 데이터 보존과 일상 사용의 장애 해결, P2는 형식 및 사용성 확장, P3는 범위가 큰 탐색 과제다. 작업 크기는 상대 추정으로 소는 단일 영역, 중은 여러 경로와 시험, 대는 형식 처리 또는 플랫폼 통합, 특대는 신규 처리 계층과 광범위한 검증을 뜻한다. 일정 추정은 아니며 상세 설계 후 조정한다. 배정됨으로 표시한 작업 외의 담당 역할은 제안이며 새 작업 배정을 뜻하지 않는다.

### 8.1 같은 이름 충돌 처리

- 상태와 우선순위: 해결됨(main 반영), P1. 작업자 PR117과 화면 [PR114](https://github.com/Team-LJY/zipelo/pull/114)가 병합됐다. 게시된 v0.1.0에는 포함되지 않는다.
- 해결 방법: [덮어쓰기], [건너뛰기], [이름 바꿔 저장]과 나머지 파일에 같은 선택 적용을 제공한다. 덮어쓰기는 새 내용을 모두 기록하고 검증한 뒤 교체하며, 교체 전 실패에는 기존 파일을 보존한다.
- 작업 크기와 담당: 대. backend는 작업자와 저장, frontend는 선택 화면, bugfix는 독립 리뷰를 담당한다. 합의된 revision 3으로 실제 작업자와 화면을 연결했다. Windows 실기에서 세 선택과 파일 내용을 확인했으며, 최종 main 통합 뒤 실기 재검증과는 구분한다.
- 수용 기준: 세 선택과 일괄 적용, 재충돌, 취소, 디스크 부족, 교체 실패를 시험한다. 교체 전 실패에는 기존 파일의 해시를 유지하고, 교체 후 오류에는 실제 저장 및 내구성 상태를 보고해야 한다. 출력 폴더 밖에 쓰지 않아야 한다. 파일과 폴더 충돌 및 링크 대상 처리 범위도 계약에서 명시한다.

### 8.2 Windows 덮어 설치

- 상태와 우선순위: 배정됨, P1. `features/windows-upgrade-install`에서 진행한다.
- 해결 방법: 기존 경로에 새 버전을 설치하되 복구 가능한 교체 절차를 마련하고 기본 앱 연결과 시작 메뉴를 유지한다.
- 작업 크기와 담당: 대. 이번 배정의 설치 구현 및 VM 검증은 bugfix, 리뷰는 frontend가 맡는다.
- 수용 기준: Windows VM에서 v0.1.0 위에 새 설치 파일을 실행해 앱 실행과 다섯 확장자 연결 유지를 확인한다. 교체 전과 도중 취소 및 실패 시 기존 설치를 복원하고 실행 중 파일 잠금도 처리한다. README는 지원하는 업데이트 경로와 버전을 구분해 갱신한다.

### 8.3 제거 후 남는 기본 앱 연결

- 상태와 우선순위: 해결됨(main 반영), P1. [PR116](https://github.com/Team-LJY/zipelo/pull/116)이 Windows 제거 안내와 Ubuntu 조건부 복원을 반영했다.
- 해결 방법: 제거 전에 다른 앱을 고르는 안내를 제공한다. Ubuntu는 설치 전 기본 앱을 기록하고 같은 사용자가 제거하며 현재 기본 앱이 Zipelo이고 이전 앱이 유효할 때만 복원한다. 사용자가 설치 후 바꾼 선택은 보존한다. Windows는 사용자 선택을 강제로 바꾸는 방식 대신 운영체제 설정 경로를 이용한다.
- 검증 범위: Windows 설치와 제거, Ubuntu 실제 사용자 홈의 복원을 VM에서 확인했다. Ubuntu의 마지막 후보 필터 수정 이후 VM 실기는 재실행하지 않았다. 이전 앱이나 기록이 없거나 다른 사용자가 제거하는 경우 자동 복원을 보장하지 않으며 수동 선택을 안내한다.
- 수용 기준: Windows와 Ubuntu에서 제거 후 다른 앱으로 파일을 열 수 있는 안내를 확인한다. 복원 기능을 넣는 경우 이전 앱 부재, 기록 부재, 다른 사용자, 설치 후 선택 변경에도 무관한 설정을 지우지 않아야 한다.

### 8.4 16 GiB 한도와 압축 폭탄 대응

- 상태와 우선순위: 해결됨(main 반영), P1. [PR121](https://github.com/Team-LJY/zipelo/pull/121)이 사용자 허용과 자원 감시를 반영했다. 압축 TAR 스트림 상한은 아래 후속 과제로 남는다.
- 해결 방법: 해제 총량과 ZIP 생성 원본 총량을 별도로 관리하고, 스트리밍과 자원 예산을 유지하면서 사용자가 큰 작업을 명시적으로 허용한다. 기본 총량 16 GiB와 항목 10,000개는 허용 후 각각 최대 64 GiB와 200,000개로 확대된다. 출력이 256 MiB 이상이면서 압축률이 1,000배를 넘으면 별도 허용을 요구한다. 압축률, 항목 수, 실행 시간 및 남은 디스크 공간을 함께 감시한다.
- 작업 크기와 담당: 대. backend는 자원 제한과 저장, frontend는 크기 안내와 승인, bugfix는 경계 및 실패 주입 시험을 맡는 안이다.
- 수용 기준: 16 GiB 바로 아래, 경계, 초과 작업과 매우 높은 압축률의 작은 입력을 시험한다. 초과 허용 후에도 정한 자원 상한에서 중단되며 취소가 반응해야 한다. ZIP 부가 구조와 암호화로 늘어나는 출력 공간도 계산하고 메모리 및 디스크 사용량을 기록한다.

- 남은 한계: TAR.GZ, TAR.BZ2, TAR.XZ의 컨테이너 해독 스트림에는 기존 상한이 남아 있어 허용 후에도 중단될 수 있다. backend의 `fix/compressed-tar-stream-limit` 후속 작업으로 분리하며 해결 완료로 계산하지 않는다.
- 검증 범위: 최종 22cb7de의 작성자 전체 local 63단계 통과 기록과 리뷰 승인을 확인했다. Windows 화면 흐름은 직전 8fe41cc에서 확인했으며 마지막 7z 헤더 집계 수정 후 실기는 재실행하지 않았다. 자원 제한은 전체 메모리 사용량이나 운영체제의 차단된 I/O 즉시 취소를 보장하지 않는다.

### 8.5 TAR.BZ2와 TAR.XZ 해제

- 상태와 우선순위: 해결됨(main 반영), P2. [PR119](https://github.com/Team-LJY/zipelo/pull/119)가 2026-11-13에 병합됐다. 게시된 v0.1.0에는 포함되지 않는다.
- 해결 내용: 순수 Rust 해제 라이브러리를 기존 TAR 처리에 연결하고 파일 선택 필터, 지원 안내, 복합 확장자의 해제 폴더 이름과 UI 상황을 갱신했다. 기존 16 GiB 한도, 여유 공간 확인 및 경로 안전 검사를 유지하며 새 라이브러리는 배포 라이선스 고지에 포함했다.
- 담당: backend 구현, frontend 화면 연동, bugfix 리뷰 및 Windows 호환 검증.
- 검증 근거: PR119 기록상 손상 XZ 인덱스 회귀를 포함한 압축 TAR 시험 17개와 전체 local의 Rust 시험 1,112개가 통과했다. 해당 local 실행은 PR118 반영 전의 짧은 경로 매핑을 사용했다. Windows 11에서 두 형식을 실제 해제해 각 4개 파일의 원본 해시 일치와 기본 파일 선택 창 표시를 확인했다.
- 남은 검증: Wayland 기본 파일 선택 창과 Windows 릴리스 설치 패키지는 미검증이다. 이 기록은 병합된 main에서 전체 시험을 다시 실행한 결과가 아니다.

### 8.6 암호 ZIP의 Windows 탐색기 호환 제외

- 상태와 우선순위: 2026-11-13 사용자 결정으로 개선 대상에서 제외한다. 구현 우선순위를 부여하지 않는다.
- 해결 방법: 현재 AES 암호 ZIP과 지원 앱 안내를 유지한다. Windows 탐색기 호환을 위한 ZipCrypto 생성 선택지는 추가하지 않는다.
- 작업 크기와 담당: 호환 기능 구현 없음. planning의 계획 및 안내 정리는 소이며 별도 backend나 frontend 구현을 배정하지 않는다.
- 수용 기준: 계획과 사용자 안내가 탐색기 호환을 지원하거나 예정한다고 표현하지 않아야 한다. 기존 AES 생성 및 해제 기능은 유지하며, 탐색기에서 암호 ZIP이 열리는 것을 출시 수용 기준으로 요구하지 않는다.

### 8.7 미리보기

- 상태와 우선순위: 검토용 범위 초안, P2. 아래 형식과 수치는 backend와 frontend 리뷰 후 총관리자가 확정한다. 구현 착수나 통신 계약 변경을 승인한 내용이 아니다.
- 최초 지원안: UTF-8 텍스트(BOM 허용)의 `.txt`, `.md`, `.log`, `.csv`, `.json`과 정적 PNG/JPEG를 읽기 전용으로 표시한다. 텍스트는 서식 없이 표시하며 HTML, SVG, PDF, 애니메이션, 다른 문자 인코딩과 외부 앱 실행은 제외한다. 작은 문서와 사진 확인에 집중해 디코더 및 화면 범위를 줄이는 안이다.
- 크기 상한안: 선택한 항목의 해제 후 크기를 텍스트 1 MiB, 이미지 8 MiB로 제한하고 초과하면 부분 표시 대신 제한 사유와 일반 해제를 안내한다. 이미지는 가로와 세로 각각 8,192픽셀 이하, 총 16,000,000픽셀 이하, RGBA 출력 64 MiB 이하를 모두 만족해야 한다. 할당 전에 크기를 확인하고 실제 읽기 및 디코딩 중에도 예산을 적용한다. 이 수치는 프로세스 전체 메모리 상한을 뜻하지 않는다.
- 처리와 화면안: 작업자가 해제와 이미지 디코딩을 맡고 앱에는 검증된 텍스트 또는 제한된 픽셀 데이터만 전달한다. 기존 wire 한도 안의 분할 전송 여부, 작업별 메모리 및 시간 예산은 두 담당자가 계약에서 합의한다. 암호 질문은 기존 흐름을 사용하며 solid 압축의 선행 데이터 처리도 전체 작업 자원 예산에 포함한다. 닫기와 선택 변경은 진행 중 작업을 취소하고 늦게 도착한 결과를 폐기한다. 외부 통신, 스크립트 실행과 사용자 폴더에 자동 저장은 하지 않는다.
- 작업 크기와 담당안: 대. backend는 제한된 해제와 디코딩 및 계약, frontend는 읽기 전용 표시와 취소, bugfix는 손상 입력 및 자원 검증을 맡는다. 새 디코더는 8.13절의 라이선스 기준과 고지를 따른다.
- 수용 기준: 정상 텍스트와 PNG/JPEG의 표시 내용을 원본과 대조하고 바이트 및 픽셀 상한 바로 아래, 경계, 초과를 시험한다. 잘못된 UTF-8, 확장자와 내용 불일치, 손상 이미지, 과도한 이미지 크기, 암호 오류 및 solid 선행 처리 초과에는 성공 표시 없이 이유를 안내해야 한다. 취소, 닫기와 빠른 선택 변경 뒤 이전 결과가 나타나지 않고 임시 자원이 정리되며 원본과 사용자 파일 해시가 유지되어야 한다. Windows와 Wayland에서 키보드로 열기와 닫기를 확인하고 추가 화면의 `--ui-scenario`, 시험 및 가이드를 같은 구현 PR에서 갱신한다.

### 8.8 분할 압축

- 상태와 우선순위: 검토용 범위 초안, P2. backend와 frontend 리뷰 후 총관리자가 형식과 이름 규칙을 확정한다. 분할 생성은 이번 단계에서 제외한다.
- 최초 지원안: `.7z.001`부터 시작하는 분할 7z의 목록 열람과 해제만 제공한다. 같은 폴더와 같은 기본 이름의 세 자리 연속 번호 `.001`부터 `.999`까지를 최대 999개로 제한하고 첫 조각을 선택하도록 안내한다. 기존 7z 처리기가 지원하는 압축 방식과 암호 범위만 대상으로 한다. `.zip.001`, `.z01`부터 마지막 `.zip`으로 이어지는 분할 ZIP, RAR과 임의 이름 조각은 제외한다. 한 가지 조각 규칙부터 검증하는 대신 ZIP 분할 사용자는 후속 지원까지 기다려야 한다.
- 처리와 화면안: 숫자 순서로 조각을 읽고 전체를 합친 영구 파일을 별도로 만들지 않는다. 처음과 중간 조각 누락, 읽기 실패와 처리 도중 변경을 안내하며 지원하지 않는 이름은 임의로 이어 붙이지 않는다. 전체 조각을 합산해 입력과 해제 예산을 적용하고 기존 큰 작업 허용, 경로 안전, 충돌 처리와 취소 흐름을 유지한다. 다른 묶음 혼입은 구조 및 무결성 검사로 검출 가능한 경우 거부하며, 형식에 식별 정보가 없는 혼입까지 사전 검출한다고 보장하지 않는다.
- 작업 크기와 담당안: 대. backend는 조각 경계 읽기와 무결성 확인, frontend는 첫 조각 선택과 누락 및 제외 형식 안내, bugfix는 독립 도구 호환과 실패 시험을 맡는다. 조각 탐색 중 링크 및 경로 이탈 방지와 변경 감지 방식은 구현 전에 계약으로 합의한다.
- 수용 기준: 독립 도구로 만든 지원 범위의 분할 7z에서 목록과 해제 파일 해시가 일치하고 헤더 및 데이터가 조각 경계를 넘는 경우도 통과해야 한다. `.009`와 `.010`의 숫자 순서, 999개 상한, 누락, 잘림, 검출 가능한 혼입, 실행 중 조각 변경 및 암호 오류를 시험하며 실패를 성공으로 표시하지 않아야 한다. 전체 합산 자원 상한과 승인 후 상한, 취소 및 기존 파일 충돌 정책을 그대로 검증하고 입력 조각을 변경하지 않아야 한다. Windows와 Wayland에서 첫 조각 선택과 오류 안내를 확인하며 제외 형식과 분할 생성 미지원을 명확히 표시하고 `--ui-scenario`, 시험 및 가이드를 함께 갱신한다.

### 8.9 7z 만들기

- 상태와 우선순위: 설계 후보, P3.
- 해결 방법: 지원할 압축 방식과 헤더 구조를 정하고 파일 및 폴더 생성부터 단계적으로 추가한다. 암호화와 solid 구성은 지원 여부를 별도로 명시한다.
- 작업 크기와 담당: 특대. backend는 작성기, frontend는 형식 선택, bugfix는 독립 도구 호환 검증을 맡는 안이다. 새 라이브러리는 8.13절의 허용 기준과 고지 절차를 따른다.
- 수용 기준: 일반 파일, 한글 경로, 빈 파일과 폴더를 생성해 Zipelo와 독립 도구에서 풀었을 때 해시 및 구조가 일치한다. 취소와 저장 실패에서 완성되지 않은 파일을 성공으로 표시하지 않는다.

### 8.10 손상 파일 복구

- 상태와 우선순위: 범위 설계 후보, P3.
- 해결 방법: ZIP의 복구 가능한 헤더 손상부터 분석하고 복구본을 별도 파일로 만든다. 복구 가능한 항목과 유실 또는 무결성 미확인 항목을 구분한다. 원본 수정이나 모든 손상의 복구를 약속하지 않는다.
- 작업 크기와 담당: 특대. backend는 탐색과 복구, frontend는 결과 및 경고, bugfix는 손상 표본 검증을 맡는 안이다.
- 수용 기준: 헤더 손상, 중간 절단, 본문 손상, 복구 불가 표본을 구분하고 원본 해시를 유지한다. 복구 가능한 파일은 기대 해시와 대조하며 불완전한 복구를 정상 완료로 표시하지 않는다. 복구 과정에도 경로 및 자원 제한을 적용한다.

### 8.11 RAR 압축과 해제 제외

- 상태와 우선순위: v0.2에서 제외. 2026-11-13 이준영 님 결정에 따라 RAR 압축과 해제 모두 도입하지 않는다.
- 재검토 조건: 라이선스 걱정 없이 쓸 방법이 확인될 때만 다시 검토한다. 공식 unRAR 코드는 사용하지 않는다.
- 작업 범위와 담당: planning은 [기존 연구](rar-license-research.md)에 결정과 미확인 사항을 남기고 bugfix가 문서를 리뷰한다. 추가 후보 출처 감사와 구현은 진행하지 않으며 RARLAB에 문의하지 않는다.
- 수용 기준: 계획과 연구 문서에 제외 및 재검토 조건을 명시하고 README의 미지원 안내와 일치시킨다. 기존 연구 결과를 후보 채택이나 법적 적합성 확정으로 표현하지 않는다.

### 8.12 나머지 위험과 검증 범위

- Ubuntu X11 의존성 누락: 해결됨(main 반영). [PR122](https://github.com/Team-LJY/zipelo/pull/122)가 `.deb` 의존성에 `libxkbcommon-x11-0`을 추가했다. 새 Ubuntu 26.04.1 X11과 Wayland VM에서 개발용 패키지 설치와 창 실행을 확인했다. 릴리스 설치 파일 검증이나 모든 압축 동작 확인을 뜻하지 않는다.

- 프로젝트 이동 후 시험 실행기 중단: 해결됨(main 반영). [PR118](https://github.com/Team-LJY/zipelo/pull/118)이 2026-11-13에 병합됐다. 시험 소켓을 상대 경로로 바인딩해 긴 절대 경로의 길이 제한을 피하며 실제 파일 위치와 기존 안전 검사를 유지한다. 작성자는 새 실제 경로에서 별칭이나 경로 매핑 없이 전체 local 63단계(Linux 빌드, 시험, Windows 교차 빌드 각 21단계) 통과를 기록했고, 리뷰어는 실행기 시험 42개와 파일 게시 시험 55개를 직접 확인했다. Windows 실제 실행 검증을 뜻하지 않는다.

- 부분 출력과 임시 파일: P1, 중. backend와 bugfix가 실패 및 취소 시 남은 출력 목록과 재정리 방법을 검토한다. 디스크 부족, 동기화 실패와 정리 실패를 주입해 성공 오표시가 없고 무관한 파일을 지우지 않는 것을 수용 기준으로 한다. frontend는 필요한 결과 안내를 맡는다.
- 플랫폼 검증 공백: P2, 중. bugfix가 Windows 재부팅 후 연결, 지원 대상으로 정한 Windows와 Ubuntu 버전, 잘못된 암호 재시도 및 실제 UI 상황 명령 실행을 확인하는 안이다. 결과에 OS 버전과 실행한 흐름을 남기고 미검증 환경을 지원 완료로 표현하지 않는다. 이미 확인한 Wayland 아이콘과 Windows 다섯 확장자 연결은 관련 변경이 있을 때 회귀 검증한다.
- 설치 파일 서명 부재: P2, 중. planning이 서명 방식과 비용을 정리하고 설치 담당과 적용 범위를 합의하는 안이다. 인증서 구매와 서명은 이준영 님 결정 대기이며, 수용 기준은 승인된 방식의 서명 검증과 실제 설치 안내 확인이다. 서명만으로 모든 운영체제 경고가 사라진다고 약속하지 않는다.
- 릴리스 문서의 시점 차이: P1, 소. planning이 다음 문서 갱신에서 게시된 v0.1.0과 과거 검증 스냅샷을 구분한다. 릴리스 노트의 미게시 문구와 과거 미검증 목록을 최신 근거와 대조하되 과거 시험이 새 버전에서도 통과했다고 확대하지 않는 것을 수용 기준으로 한다.

### 8.13 진행과 완료 판단

- 충돌 처리, 제거 뒤 기본 앱 정리, 큰 작업 허용과 압축 폭탄 대응, X11 의존성 누락은 main에서 해결됐다. TAR.BZ2/XZ와 프로젝트 이동 후 시험 실행기 중단도 해결됐으며 압축 TAR 스트림 상한은 후속 과제로 남는다. 8.7과 8.8은 두 담당자 리뷰 및 총관리자 범위 확정 대기인 초안이다. RAR 압축과 해제는 v0.2에서 제외하며 라이선스 걱정 없이 쓸 방법이 확인될 때만 다시 검토한다. 암호 ZIP의 Windows 탐색기 호환은 목표에서 제외한다. 나머지 후보의 우선순위와 크기는 검토안이며 동시 착수를 지시하지 않는다.
- 2026-11-13 사용자 결정과 갱신된 팀 규칙에 따라 순수 Rust이고 MIT, Apache, BSD, zlib 같은 자유 라이선스인 외부 라이브러리를 사용할 수 있다. 도입 PR에 선택 이유와 라이선스 고지를 포함하고 packaging/licenses.py의 배포 고지에 반영한다. 이 기준 밖의 의존성은 사전 확인을 받는다. RAR 압축과 해제 제외 및 공식 unRAR 코드 사용 금지는 별도로 유지한다. 공용 계약은 backend와 frontend 합의가 선행되어야 한다.
- 제품 변경 PR은 해당 회귀 시험과 `python3 tests/ci/run_rust.py local` 결과를 기록하고, 설치 변경은 패키지 시험과 플랫폼 실기를 포함한다. 시험 및 시험용 도구는 프로젝트 루트의 `tests/` 아래에만 둔다.
- 화면이 바뀌면 같은 PR에서 `--ui-scenario` 상황, 시험 및 [상황별 UI 가이드](ui-scenario-guide.md)를 함께 갱신한다. 화면 변화가 없으면 PR 본문에 "UI 변경 없음"을 적는다. 사용자가 직접 올린 UI PR의 누락은 병합 뒤 frontend가 보완한다.
- 각 기능의 실제 병합 및 검증 근거가 확보된 뒤 README와 릴리스 노트의 해당 한계를 갱신한다. 전체 후보를 한 번에 완료해야 한다고 가정하지 않고, 다음 출시 범위와 미해결 항목을 별도로 합의한다. 릴리스 게시는 별도 승인을 따른다.
