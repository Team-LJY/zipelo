# Core 경합과 종료 처리 수정

## 범위와 검증 상태

2026-11-09의 [보안 검토](SECURITY_REVIEW.md) 4~6장을 기준으로 암호 요청 경합과 초기화 실패 시 출력 정리 누락을 수정했다. src/Zipelo.Core의 ArchiveJob.cs, EngineContext.cs와 ArchiveContracts.cs만 수정했으며 tests/와 Desktop은 수정하지 않았다. 공개 타입, 메서드 시그니처, enum 값과 결과 필드는 그대로다.

로컬 PATH에서 dotnet과 C# 컴파일러를 찾지 못했다. 이번 확인은 소스 흐름과 기존 테스트 대역 대조, 공백 및 프로젝트 XML 검사뿐이며 C# 컴파일이나 회귀 실행 통과를 뜻하지 않는다. Windows 스냅샷의 이전 결과는 이번 수정의 검증 근거가 아니다. Windows 복사와 재검증은 총괄이 별도로 조율한다.

## 암호 요청과 상태

[EngineContext](../src/Zipelo.Core/EngineContext.cs)의 전용 SemaphoreSlim이 작업별 PasswordProvider 호출을 직렬화한다. 시도 번호는 잠금 안에서 증가시킨 지역값으로 전달하며 제한 확인을 증가보다 먼저 해 정수 넘침도 피한다. 대기 중 취소된 요청은 제공자를 호출하거나 시도 횟수를 소비하지 않는다. FIFO 순서는 보장하지 않는다.

WaitingForPassword는 실제 제공자가 응답을 기다리는 동안만 유지한다. 다른 항목의 목록 및 복사 진행이 이 상태를 Running으로 덮지 못하도록 상태 잠금을 사용한다. 제공자가 반환하면 상태와 잠금을 복원하고 소비 콜백은 잠금 밖에서 실행한다. 따라서 소비 콜백의 추가 암호 요청은 가능하지만 제공자 자체가 같은 작업의 암호 요청을 재진입하고 기다리는 동작은 금지한다.

암호는 소비 종료까지 요청별로 소유하며 성공, 소비 예외, 취소와 늦은 제공자 응답 모두에서 finally로 폐기한다. 취소 뒤 반환된 암호는 소비 전에 예산 및 취소 검사에 걸려 폐기된다. 제공자가 영원히 반환하지 않으면 Core가 아직 받지 못한 암호를 폐기할 수 없으며, 이 수정은 강제 종료를 구현하지 않는다. 서로 다른 소비 콜백이 동시에 실행될 수 있으므로 엔진은 시작한 작업을 전부 await해야 한다.

UI 연결 시 제공자 중복 호출은 없어지고 WaitingForPassword의 의미가 제공자 응답 대기로 좁아진다. 진행 이벤트는 Sequence 순서를 기준으로 적용해야 한다. 비동기 IProgress 구현의 큐 처리 순서까지 Core가 보장하지 않는다.

## 초기화와 출력 소유권

[ArchiveJob](../src/Zipelo.Core/ArchiveJob.cs)은 필수 인자의 null 검사와 일회 실행 확인이 끝난 시점부터 출력 소유권을 받는다. 이 사전 검사에서 거부된 호출의 출력은 호출자가 소유한다. 그 뒤 JobBudget 생성, 연결 취소 토큰 생성, 입력 목록 복사와 문맥 초기화는 모두 출력 DisposeAsync를 호출하는 try/finally 안에서 수행한다.

제한값 오류 등 문맥 생성 전 ArgumentException은 Failed/UnsupportedOperation 결과와 빈 항목 목록으로 반환한다. 초기화 전에 실패한 예산의 진행량은 0이다. 입력 목록 복사 등 그 밖의 예외도 정리를 거친 뒤 오류 결과를 반환한다. 실패한 작업 인스턴스는 재사용하지 않는다. 출력 정리는 정확히 한 번 시도하며 정리가 반환해야 종료 이벤트를 보낸다.

정리도 실패하면 작업 상태는 Failed로 한다. 기존 주 오류가 있으면 보존하고, 주 오류가 없을 때만 OutputUnavailable을 기록한다. 공개 JobResult에는 별도 정리 오류 필드가 없어 두 오류를 독립적으로 표현하지 못한다. 이 제약을 숨기거나 오류 원문에 암호 또는 경로를 넣지 않는다. 특히 Failed/Cancelled는 취소 뒤 정리 실패가 있었을 수 있으므로 정상 취소 완료로 표시하면 안 된다.

## 게시 실패와 취소 완료 계약

[IOutputTransaction](../src/Zipelo.Core/ArchiveContracts.cs)은 전체 게시 성공 또는 실패 시 작업 소유 출력 원복을 요구한다. 두 번째 파일에서 실패했다면 이미 게시한 첫 번째 파일도 원복해야 하며, 원본과 작업 전부터 있던 파일은 건드리지 않아야 한다. 부분 게시 결과를 돌려줄 수 없는 현재 인터페이스에 부분 성공 저장 계층을 그대로 연결하지 않는다.

이것은 저장 구현의 의무를 명확히 한 것이며 원자적인 Windows 파일시스템 동작을 구현한 것이 아니다. 현재 실제 구현은 UnavailableOutput뿐이다. 기존 메모리 테스트 대역도 일반적인 부분 게시 후 실패와 원복을 입증하지 않는다. 저장 계층이 원복에 실패하거나 프로세스가 중단되면 현재 결과만으로 남은 파일을 정확히 나열할 수 없다. 그런 저장 방식을 채택하려면 별도의 항목별 게시 결과 및 복구 계약이 먼저 필요하다.

- CommitAsync 정상 반환: Staged는 Extracted로 변환한다. 반환 직전이나 직후의 늦은 취소로 실제 게시 성공을 Cancelled로 덮지 않는다. 이후 정리가 실패하면 작업은 Failed여도 항목의 Extracted를 유지한다.
- CommitAsync 실패 또는 취소: Staged는 Failed로 변환한다. 이는 게시 성공을 확인하지 못했다는 의미다. 저장 계층의 원복 및 정리 성공 근거 없이 파일이 없다고 안내하면 안 된다. Partial 값은 예약 상태이며 이번 구현에서 실제 부분 성공 판정에 사용하지 않는다.
- 출력 없는 작업: 엔진과 모든 문맥 작업이 끝난 뒤 마지막 예산 및 취소 검사를 통과하면 완료 경계를 지난 것으로 본다. 이후의 취소는 이미 끝난 결과를 되돌리지 않는다.
- Cancelled 종료: 협력하는 엔진 호출이 반환하고 출력 정리가 성공한 뒤에만 보고한다. 정리가 실패하면 Failed다. 취소 등록을 해제한 뒤 최종 이벤트를 보내며 취소가 확인된 상태에서 Running이나 WaitingForPassword를 새로 보고하지 않는다.

비협력 엔진, 멈춘 암호 제공자 또는 DisposeAsync를 강제로 종료하지 않는다. Windows 링크/junction 방어, 실제 안전 출력, 별도 작업 프로세스, 메모리 및 시간 강제 제한은 여전히 미구현이다. Completed는 CRC 또는 인증 검증 통과와 동의어가 아니며 항목의 Verification을 별도로 유지한다.

## 필요한 회귀 사례

다음은 테스트 담당자가 기존 29개 컴파일 및 실행 확인 이후 추가할 사례다. 이번 라운드에서는 테스트를 작성하거나 실행하지 않았다.

1. 두 암호 요청을 겹치고 첫 제공자 응답을 지연한다. 제공자 동시 실행 최대값 1, 서로 다른 RequestId와 시도 번호 1/2, 다른 항목 진행 중 WaitingForPassword 유지, 각 소비자에게 자기 암호 전달을 확인한다.
2. 첫 암호 요청 대기 중 두 번째 요청과 작업을 취소한다. 두 번째 제공자 미호출, 늦게 반환된 첫 SecureString 폐기, 소비자 미호출, 최종 취소 뒤 비종료 이벤트가 없음을 확인한다.
3. 제공자 예외, 소비자 예외와 재요청 뒤에도 게이트가 풀리는지 확인한다. 소비자 안의 재요청이 교착하지 않는지와 시도 상한 뒤 추가 제공자 호출이 없는지도 확인한다.
4. null 또는 잘못된 JobLimits와 입력 목록 복사 예외를 주입한다. 엔진 미실행, 출력 정리 한 번, 빈 항목 또는 기존 항목 보존, 최종 오류 이벤트를 확인한다. 재사용 및 사전 null 인자 거부는 출력 소유권 이전 전인 점도 구분한다.
5. IntegrityFailure 뒤 정리 실패에서는 주 오류를 보존하며 Failed를 반환하는지 확인한다. 취소 뒤 정리 실패도 Cancelled 종료가 아닌 Failed인지 확인한다.
6. 두 항목의 첫 게시 뒤 실패하거나 취소되는 저장 대역에서 작업 소유 게시의 원복과 기존 파일 불변을 확인한다. 원복 실패는 성공으로 숨기지 않으며 결과만으로 파일 부재를 주장하지 않는다. 실제 Windows 저장 구현에서도 별도 검증이 필요하다.
7. CommitAsync가 게시를 완료하고 토큰을 취소한 뒤 정상 반환하면 Completed/Extracted를 유지하는지 확인한다. 게시 성공 뒤 DisposeAsync 실패는 Failed/Extracted를 유지해야 한다.
8. 출력 정리를 지연하면 정리가 끝나기 전 최종 이벤트와 ExecuteAsync 완료가 없는지 확인한다. 멈추는 대역 검사는 외부 실행 시간 제한이 있는 환경에서만 수행한다.
